Error reference

NY001-NY013 are gateway SQLSTATEs with fixed, data-free messages. Each refusal below includes a genuine trigger condition and a recovery path.

Read codes, not sensitive details

Gateway refusals have fixed five-character SQLSTATEs. PostgreSQL ErrorResponse fields contain severity ERROR, the NY code and a fixed public message. JSON grouping and ordering refusals distinguish a blind, masked or unlisted path from a path without a single rule covering the leaf. Choose recovery by SQLSTATE rather than parsing message text.

In native Spanner gRPC, NY004 maps to INVALID_ARGUMENT; NY008 and NY009 map to FAILED_PRECONDITION; NY011 maps to PERMISSION_DENIED; NY012 maps to UNKNOWN. NY010 for an unreachable Spanner upstream before sending maps to UNAVAILABLE; protocol refusals and the other NY codes map to PERMISSION_DENIED. The public status message includes the NY code and the same fixed message.

The SQL examples assume the shipped policy and harness tables unless stated otherwise. A condition-dependent refusal is explicitly labeled: SQL alone cannot create a stale snapshot, a full log disk or a protocol violation.

NY001 - Crossing a domain or plaintext boundary

NY001: token used outside its domain

Assume the harness schema: customers.email is blind and notes.body is plain. Copying a protected column to a plain destination is forbidden. This statement reaches NY001 without needing a fabricated token:

INSERT INTO notes (id, body) SELECT id, email FROM customers WHERE id = 3;

If customers.email and customers.full_name are blind in different domains, SELECT email FROM customers UNION SELECT full_name FROM customers also gives NY001.

Fix: Use the same declared blind domain on both sides of a set operation or write, such as the example outbox.to_address and customers.email.

NY002 - Inspecting a blind value

NY002: operation not allowed on a blind column

With the example email policy, a pattern test needs access to hidden content:

SELECT email FROM customers WHERE email LIKE 'a%';

A CASE expression that returns a blind value also gives NY002. COALESCE gives NY002 when it mixes a blind column with a plain value, a literal, a parameter, or a column in a different blind domain.

Fix: Use permitted equality with a valid token or analytics on plain columns. A COALESCE output can use bare blind columns that share one domain and column type.

NY003 - Invalid token or session scope

NY003: token not valid in this session

A malformed text token or one from another session scope fails authentication. Authentication failures, including a principal credential sent to a database port, are indistinguishable from an unknown user and also use NY003.

A plaintext value in a position that expects a token also gives NY003. This includes a guessed email supplied as a literal or bound parameter. On the native Spanner GoogleSQL route literals are never decrypted, so any string literal in a token position, including a pasted token, gives NY003; bind tokens as query parameters.

SELECT id FROM customers WHERE email = 'olivia.smith@example.com';

Fix: Use an unmodified token from the active session and its session credential. Reconnect or renew to preserve scope. A replacement session requires fresh tokens. Format-preserving typed tokens lack an authentication marker, so foreign-scope misuse is not reliably detected. See token concepts.

NY004 - Incomplete analysis

NY004: statement could not be fully analysed

Nunya refuses catalog surfaces that could expose protected information. This corpus example is refused during analysis:

SELECT * FROM pg_stats;

Fix: Use supported table queries. For other analysis failures, simplify the query to supported statement shapes and inspect the schema snapshot. An unknown object, unsupported syntax or unresolved expression is not passed through without full analysis.

NY005 - Using a masked column as an expression

NY005: masked column used in an expression

With phone masked by the example policy, its value cannot be tested:

SELECT id FROM customers WHERE phone IS NOT NULL;

Fix: Project phone directly to obtain its configured placeholder or NULL, or remove the predicate. Masked values cannot participate in expressions, filters or joins. NY005 also covers PostgreSQL DISTINCT over masked outputs, refused JSON paths (R1 whitespace-prefixed PostgreSQL elements and R3 digit-only GoogleSQL key steps), and non-text blind JSON leaves in predicates; see JSON paths.

NY006 - Refused statement kind

NY006: statement kind not allowed through the gateway

Schema changes are outside the gateway statement surface:

CREATE TABLE agent_copy (id integer);

Fix: Perform administration through an authorized operator route outside the agent gateway. A read-only session also refuses write statement kinds; on native Spanner this includes DML, Commit mutations and BatchWrite. Other NY006 cases include mixing harmless no-op SET statements with normal statements and requesting tokenize-from-plain for an off domain.

NY007 - Tokenize quota exhausted

NY007: tokenize limit reached

Explicit plaintext tokenization has exhausted the domain's tokenize_limit_per_session or tokenize_limit_per_principal within tokenize_principal_window. Both counters are durable; reconnecting or restarting cannot clear them.

SELECT nunya_tokenize('email', 'new@example.com');

Fix: Reduce explicit tokenization calls. Wait for the principal window to end if its limit was reached, or have an operator review the policy limits. A new session does not reset the principal counter. Ordinary SELECT output tokenization is separate.

NY008 - Stale schema snapshot

NY008: schema snapshot is stale

Prerequisite: the current snapshot is older than the policy maximum age, for example because catalog refresh has repeatedly failed. A query then fails before analysis:

SELECT id FROM customers;

NY008 also fences further result release after a tightened policy revision, for every open statement on that route. The fixed message remains schema snapshot is stale.

Fix: Restore catalog connectivity and resolve validation failures so a fresh safe snapshot can be published. Failed refreshes keep the old snapshot; increasing maximum age trades away freshness and does not repair the underlying failure.

NY009 - Unavailable read log

NY009: read log unavailable

Prerequisite: the configured read-log sink fails, for example its writable filesystem is full. A statement requiring a durable intent record is refused before it can execute upstream:

SELECT email FROM customers;

NY009 also covers failures writing completion or token-release records, and unavailable durable accounting for explicit tokenization. It does not by itself prove a forwarded operation never ran.

Fix: Restore the sink's availability, disk space and permissions. Recheck configuration and storage access as the service account. Do not bypass the log to make the request succeed.

NY010 - Unsupported protocol traffic

NY010: protocol feature not allowed through the gateway

This is a protocol refusal, not a SQL-only trigger. For example, a frontend CopyData frame (message tag d) is not an accepted request. The following is an illustrative wire description, not a shell or SQL command:

Frontend frame: CopyData (tag d), payload bytes

NY010 also reports an upstream connection failure when no write was in flight; retrying a read is safe in that case. On the native Spanner route, an unreachable upstream before anything is sent returns NY010 / gRPC UNAVAILABLE, without an unknown-write audit record; retrying is safe.

Fix: Use supported PostgreSQL simple or extended query messages and a tested driver. Unsupported traffic, malformed frames and invalid protocol sequencing fail closed. A SQL COPY statement can instead fail as a refused statement kind (NY006); it is not an example of a CopyData frame.

NY011 - Access session ended

NY011: access session ended

An authenticated connection's session expired (absolute or idle), was revoked, or ended because its principal was disabled, its standing configuration was removed or its route grant was removed. PostgreSQL also refuses with NY011 if a refreshed snapshot no longer captures every schema in the connection's pinned search_path. Native Spanner returns PERMISSION_DENIED. PostgreSQL cancels upstream work, relays no further rows, sends one error and closes the connection. After the error Nunya half-closes and briefly drains the connection, so a client that writes promptly or reads the socket still reads NY011 before the close (limits below).

Fix: Stop using that connection. For an uncaptured pinned search path, have an operator restore safe schema capture or reconnect with the configured path. Check session state through management, then explicitly acquire a replacement scope and obtain fresh tokens if authorized. Do not silently replace the scope.

After a final error, the gateway half-closes the connection and drains input for up to 1.5 seconds or 1 MiB. A client that reads the socket sees NY011. A client that stays idle longer than this window and then writes without reading first may, on Windows, see a connection reset instead: its OS discards the unread error. Retrying on a new connection gets the usual NY003/NY011-style refusals.

NY012 - Write outcome unknown

NY012: write outcome unknown

A write or COMMIT was forwarded and the access session ended, or the upstream connection was lost, before its completion was seen. This applies to both PostgreSQL and native Spanner, including forwarded DML. A native Spanner Commit response without a commit timestamp also gives NY012. The database may or may not have applied it. Native Spanner returns UNKNOWN. Nunya replays nothing. Every NY012 writes a data-free write_outcome_unknown audit record; see logging.

Fix: Reconcile the outcome with application identifiers or an authorized operator before retrying. A blind retry may duplicate a write.

NY013 - Serving lease lapsed

NY013: serving lease lapsed

With the Kubernetes policy store, a pod serves only while it holds a current serving lease and has loaded the active policy revision. A pod that cannot renew its lease within the term (for example while it cannot reach the Kubernetes API server), or that has just started, refuses new connections and stops releasing rows from running statements, portals and streams; the connection is then closed. Native Spanner returns UNAVAILABLE, or UNKNOWN for forwarded DML. See operations.

Fix: Retry on a new connection after a short wait; another pod or the same pod after it renews will serve. Ask the operator to check API-server reachability if it persists.

Upstream errors and redaction

Not every error is a Nunya refusal. PostgreSQL upstream errors retain a validated uppercase/digit five-character SQLSTATE (or XX000 for an invalid one), but arbitrary messages, details and hints are replaced or removed. Duplicate-key SQLSTATE 23505 has the fixed message "duplicate key value violates unique constraint"; foreign-key SQLSTATE 23503 becomes "foreign key violation". Other errors use a generic message for their SQLSTATE class or "database error".

Native upstream gRPC errors preserve their status code with a fixed generic message, and drop original details and metadata. This prevents database diagnostics from echoing blind values. If a transaction has aborted, recover with the appropriate rollback rather than repeatedly issuing the failed query. See SQL support and operations.
