Drivers

Connect PostgreSQL clients to Nunya's listener with the session credentials supplied by nunya exec. The SQL policy applies regardless of the driver; a working handshake does not make every driver-generated statement supported.

What has been exercised

ClientEvidence and scope
psycopg 3.3.9 with psycopg-pool 3.3.3 (Python 3.13.3)Prepared statements, text parameters/results, pooled round trips on distinct connections, gateway restart recovery, revocation and expiry.
pgJDBC 42.7.14 with HikariCP 7.1.0 (slf4j-api 2.0.17, Temurin 21.0.7)HikariCP is supported: pool start, pooled round trips, gateway restart recovery, revocation and expiry. Extended mode, prepare threshold 1 and binary transfer disabled.
tokio-postgres 0.7.15Used in service, non-interference and PGAdapter integration tests.
PostgreSQL 18.6 upstreamUpstream for the private harness.

The psycopg and JDBC checks read blind emails, write one to the same domain, check stable token output, refuse a token into plain notes, refuse blind LIKE, query a missing plain-country row, and verify the masked phone placeholder. Their main modes have 12 and 13 steps respectively; each expiry mode has three. Run against freshly seeded harness data. No driver changes are needed for the tested workflows; point connection settings to Nunya and respect its supported SQL subset.

Private harness

bash harness/run.sh private [--work-root DIR] [--nunya-exe PATH] [--linux-bin PATH]

The harness runs these scenarios: bootstrap (session acquisition and reuse), private_network (tool isolation from the upstream database), psycopg, psycopg_expiry, jdbc and jdbc_expiry. The main driver scenarios exercise pools, restart recovery and revocation; the expiry scenarios verify that ended sessions reject both open and new connections. A failed HikariCP pool start fails the JDBC check immediately; it does not switch connection types.

NUNYA_PROJECT_PREFIXCompose project prefix, default gd81-d1; lowercase letters, digits, underscores and hyphens, starting with a letter or digit. The harness appends a process ID and random suffix.

Python dependencies are pinned in harness/drivers/requirements-psycopg.txt (including psycopg-binary==3.3.9). JDBC artifacts are pinned with SHA-256 hashes in harness/drivers/jdbc-jars.txt; fetch-jdbc.sh downloads missing JARs and verifies both new and existing files. The harness uses Java 21 single-file source launching.

The driver checks read connection settings only from the PG* environment variables set by nunya exec, using the session login session:<id>. Principal credentials authenticate to management, while session credentials authenticate to database ports. See Access sessions and exec and Agent instructions. Keep credentials out of command arguments and output.

Check results print only PASS/FAIL step names and totals, with sanitized refusal SQLSTATE details. The scripts also emit WAIT restart, WAIT revoke or WAIT expiry control markers for the harness; they print no returned values, tokens, credentials or exception messages.

Pools and session metadata

The PostgreSQL route forwards exactly these session-metadata statements: SHOW transaction_isolation, SHOW TRANSACTION ISOLATION LEVEL, SELECT current_schema(), SELECT current_database() and SELECT current_catalog. The empty query in extended mode is answered locally for JDBC isValid(). Any other SHOW is refused with NY006; variants with FROM, WHERE, LIMIT or other clauses are refused. See Errors.

psycopg connection

import psycopg

with psycopg.connect(
    dbname='app',  # PGHOST, PGPORT, PGUSER and PGPASSWORD come from nunya exec.
    sslmode='disable',
    autocommit=True,
) as conn:
    with conn.cursor() as cur:
        cur.execute('SELECT id, email FROM customers WHERE failed_payments >= %s',
                    (2,), prepare=True)
        rows = cur.fetchall()
        # Keep token values opaque; carry them only to approved destinations.

Run this application under nunya exec as described in the CLI reference. The private harness supplies the driver-check mode and session environment itself.

pgJDBC connection

Properties properties = new Properties();
properties.setProperty("user", System.getenv("PGUSER"));
properties.setProperty("password", System.getenv("PGPASSWORD"));
properties.setProperty("preferQueryMode", "extended");
properties.setProperty("prepareThreshold", "1");
properties.setProperty("binaryTransfer", "false");
properties.setProperty("stringtype", "unspecified");
Connection connection = DriverManager.getConnection(
    "jdbc:postgresql://" + System.getenv("PGHOST") + ":" +
    System.getenv("PGPORT") + "/app?sslmode=disable", properties);
connection.setAutoCommit(true);
PreparedStatement query = connection.prepareStatement(
    "SELECT id, email FROM customers WHERE failed_payments >= ?");
query.setInt(1, 2);
ResultSet rows = query.executeQuery();

The private harness starts the pinned HikariCP pool and manages the session environment. This direct connection fragment shows the pgJDBC settings; the check uses two simultaneous pool leases for its distinct-connection round trip.

tokio-postgres connection

let mut config = tokio_postgres::Config::new();
config.host(&std::env::var("PGHOST")?);
config.port(std::env::var("PGPORT")?.parse()?);
config.dbname("app");
config.user(&std::env::var("PGUSER")?);
config.password(std::env::var("PGPASSWORD")?);
let (client, connection) = config.connect(tokio_postgres::NoTls).await?;
tokio::spawn(async move { let _ = connection.await; });
let rows = client.query(
    "SELECT id, email FROM customers WHERE failed_payments >= $1",
    &[&2_i32],
).await?;

This fragment belongs in an async Rust application that already handles errors and runs Tokio. NoTls is for the explicitly plaintext local harness. For a deployed listener, configure certificate verification in the client's TLS connector.

Compatibility checklist

Keep session tokens opaque, preserve their apparent SQL types, bind them only in the permitted domain, and handle Nunya SQLSTATE refusals. Send initial no-op SET statements separately from application SQL. Choose explicit text parameter/result formats when reproducing the published driver checks. Do not enable driver discovery, migration, COPY, partition or metadata workflows without checking their statements against SQL support. For native gRPC authentication and GoogleSQL parameters, use the Spanner guide.
