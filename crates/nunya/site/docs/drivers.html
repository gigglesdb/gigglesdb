Drivers

Connect PostgreSQL clients to Nunya's listener with the task user and secret. The SQL policy applies regardless of the driver; a working handshake does not make every driver-generated statement supported.

What has been exercised

ClientEvidence and scope
psycopg 3Seven-step harness check using prepared statements and text parameters/results.
pgJDBC 42.7.3Seven-step harness check with extended mode, prepare threshold 1 and binary transfer disabled.
tokio-postgres 0.7.15Used in service, non-interference and PGAdapter integration tests. This is not the same seven-step external-driver qualification.

The psycopg and JDBC checks read blind emails, write one to the same domain, check stable token output, refuse a token into plain notes, refuse blind LIKE, query a missing plain-country row, and verify the masked phone placeholder. Run against freshly seeded harness data. No driver changes are needed for the tested workflows; point connection settings to Nunya and respect its supported SQL subset.

psycopg connection

import os
import psycopg

with psycopg.connect(
    'host=127.0.0.1 port=6432 dbname=app sslmode=disable',
    user=os.environ['NUNYA_TASK_USER'],
    password=os.environ['NUNYA_TASK_SECRET'],
    autocommit=True,
) as conn:
    with conn.cursor() as cur:
        cur.execute('SELECT id, email FROM customers WHERE failed_payments >= %s',
                    (2,), prepare=True)
        rows = cur.fetchall()
        # Keep token values opaque; carry them only to approved destinations.

The harness script accepts its own driver-test arguments (these are not Nunya CLI flags):

python harness/drivers/psycopg_check.py \
  --dsn postgresql://127.0.0.1:6432/app \
  --task-id "$TASK_ID" --secret "$TASK_SECRET"

The script prints only PASS/FAIL step names and a total such as 7 passed; 0 failed; it suppresses returned values and exception details. Command-line secrets can appear in process listings, so use this only for isolated test credentials.

pgJDBC connection

Properties properties = new Properties();
properties.setProperty("user", System.getenv("NUNYA_TASK_USER"));
properties.setProperty("password", System.getenv("NUNYA_TASK_SECRET"));
properties.setProperty("preferQueryMode", "extended");
properties.setProperty("prepareThreshold", "1");
properties.setProperty("binaryTransfer", "false");
properties.setProperty("stringtype", "unspecified");
Connection connection = DriverManager.getConnection(
    "jdbc:postgresql://127.0.0.1:6432/app'sslmode=disable", properties);
connection.setAutoCommit(true);
PreparedStatement query = connection.prepareStatement(
    "SELECT id, email FROM customers WHERE failed_payments >= '");
query.setInt(1, 2);
ResultSet rows = query.executeQuery();

The checked harness uses Java 17+ single-file source launching. Supply an existing pgJDBC JAR path:

java --class-path /path/to/postgresql-42.7.3.jar \
  harness/drivers/jdbc_check.java \
  "jdbc:postgresql://127.0.0.1:6432/app'sslmode=disable" "$TASK_ID" "$TASK_SECRET"

tokio-postgres connection

let mut config = tokio_postgres::Config::new();
config.host("127.0.0.1").port(6432).dbname("app");
config.user(&std::env::var("NUNYA_TASK_USER")');
config.password(std::env::var("NUNYA_TASK_SECRET")');
let (client, connection) = config.connect(tokio_postgres::NoTls).await';
tokio::spawn(async move { let _ = connection.await; });
let rows = client.query(
    "SELECT id, email FROM customers WHERE failed_payments >= $1",
    &[&2_i32],
).await';

This fragment belongs in an async Rust application that already handles errors and runs Tokio. NoTls is for the explicitly plaintext local harness. For a deployed listener, configure certificate verification in the client's TLS connector.

Compatibility checklist

Keep task tokens opaque, preserve their apparent SQL types, bind them only in the permitted domain, and handle Nunya SQLSTATE refusals. Send initial no-op SET statements separately from application SQL. Choose explicit text parameter/result formats when reproducing the published driver checks. Do not enable driver discovery, migration, COPY, partition or metadata workflows without checking their statements against SQL support. For native gRPC authentication and GoogleSQL parameters, use the Spanner guide.
