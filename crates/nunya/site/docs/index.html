A working boundary for database agents

Nunya is a separate lane for AI agents only. Applications keep their existing direct database connections; agents get useful SQL access with protected values returned as tokens.

Start with a real query

An agent following up on missed payments needs customer identifiers and a way to queue reminders. It does not need to see an email address. Nunya lets it carry a token from a protected customer column to an approved outbox column. The database stores the real address; the agent reads the token again.

Understand the boundary first

Every sensitive column must be marked in the policy. An unmarked column is plain and passes through. The agent must have no direct route to the upstream database and must never receive upstream credentials. Protect the Nunya host, root key, state directory, principal and session secrets and logs.

Principals authenticate only to management to acquire access sessions. Agents use session credentials on database ports. Each session carries a persisted token scope, so reconnects and renewals keep tokens usable; revocation or expiry ends access. A new scope requires fresh tokens. Tokens preserve equality within a domain and scope. Repeated values and counts can remain visible. Nunya is a controlled SQL gateway, not a promise to hide every fact about a dataset. Read Security and Limitations before exposing a route.

PostgreSQL and two Spanner routes

PostgreSQL agents connect over the PostgreSQL wire protocol. Spanner can use that route through PGAdapter, or a native GoogleSQL gRPC route.

Nunya's live tests run the worked example and the access-session tests against real PostgreSQL 16.16, 17.12 and 18.6 servers. The driver guide records the current psycopg and pgJDBC/HikariCP versions and private-harness checks. These are specific compatibility results, not a claim that every driver or query is supported.
