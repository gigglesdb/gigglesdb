Operations

Run Nunya as a dedicated unprivileged service with private configuration, writable state and a read log. Keep upstream credentials and the database network inaccessible to agents.

Deployment shape

Give Nunya its own database role, configured by [upstream] user, with only the grants the agent workflows need. Provision principals and route grants, then give each workflow an access session. Use an isolated session when workflows need separate token scopes. Let agents reach only Nunya's listener, never the database itself, and keep upstream credentials outside the agent environment.

Leave application traffic on its existing direct connection. Do not route application traffic through Nunya: it refuses DDL and anything it cannot analyse, returns tokens instead of protected values, and is built for agent access.

Container and service layout

docker build -f crates/nunya/Dockerfile -t nunya .

Run that build from the repository root. The multi-stage Dockerfile builds the release binary on rust:1-bookworm with clang/libclang-dev, then copies it into debian:bookworm-slim. It runs as uid/gid 10001 and exposes 6432. Its default command is serve --config /etc/nunya/nunya.toml. This page documents the recipe; it does not claim a published registry image.

docker run --rm --name nunya \
  -p 127.0.0.1:6432:6432 \
  --mount type=bind,src=/absolute/private/config,dst=/etc/nunya,readonly \
  --mount type=bind,src=/absolute/private/state,dst=/var/lib/nunya \
  nunya

Replace both absolute host paths. In the mounted configuration, set state_dir to /var/lib/nunya, listen to 0.0.0.0:6432 so Docker can forward to it, and upstream host to an address reachable from the container. Container loopback is not the host database. Pre-create the state directory owned by uid 10001 and mount root-key, password and TLS files read-only with permissions that uid can read. Keep admin private; the example does not publish its port.

For a host service use a dedicated account and run nunya serve --config /etc/nunya/nunya.toml. Configuration/service errors exit 1; clean shutdown exits 0.

TLS and secrets

Inbound [tls] requires cert_file and key_file. Without it, explicit allow_plaintext = true is required. Both routes share these files. Keep private keys and root keys out of source control, errors and shell history. Relative file paths are resolved beside the configuration.

For PostgreSQL upstream upstream.tls, disable is plaintext; require encrypts but accepts any certificate; verify-full checks the hostname using ca_file as the only trust root. Configure the agent client to verify the inbound server certificate as well. These are separate TLS connections.

[tls]
cert_file = "server-chain.pem"
key_file = "server-key.pem"

[upstream]
host = "db.internal"
port = 5432
user = "nunya"
dbname = "app"
password_file = "upstream.password"
tls = "verify-full"
ca_file = "database-ca.pem"

The fragment must be combined with a complete top-level configuration and policy. root_key_file and password_file take precedence over their environment alternatives, NUNYA_ROOT_KEY and NUNYA_UPSTREAM_PASSWORD.

Private-network reachability

Configure [management] listen for authenticated JSON over HTTP/1.1. Non-loopback addresses require tls with cert_file and key_file; configuration without it is refused. Give operators and agents private-network reachability to management for session lifecycle operations, with principal credentials and only the grants they need. Session credentials are refused by management.

[management]
listen = "10.0.0.5:6481"
tls = { cert_file = "management-chain.pem", key_file = "management-key.pem" }

On Unix, the service creates state_dir/nunya.sock, mode 0600, owned by the service user. The socket path state_dir/nunya.sock must be at most 107 bytes; Nunya refuses to start otherwise. Requests through it carry administrator authority: protect the directory and access to that account. Use this socket to provision the first principal. Windows has no socket; bootstrap with [[management.admin]] entries containing name and verifier. Generate the verifier with nunya standing hash and protect it as a credential. See provisioning and configuration.

The separate unauthenticated admin listener defaults to 127.0.0.1:6480 through admin_listen. Its health, metrics, status and reload routes have no TLS or authentication. Keep it private and inaccessible to agents. It does not issue sessions.

Health and readiness

GET /health on the admin listener is liveness only: a 200 response with body ok proves that endpoint responds, not that upstream queries can run. Readiness must establish policy and catalog state, audit availability and store availability for every route.

GET /ready on the admin listener is readiness: it reports, for each configured route, whether the policy and catalog state are usable, whether the read log can take records and whether the state store is available. Use it, not /health, for load-balancer and orchestrator readiness probes, in PostgreSQL-only, Spanner-only and combined deployments alike.

The response is plain text with one line per configured route, for example route=postgres policy=ok catalog=ok audit=ok store=ok. policy, audit and store are ok or unavailable; catalog is ok, stale (the snapshot is older than the policy maximum age) or unavailable (the route has not loaded its first catalog yet). The status is 200 only when every route reports ok for all four; otherwise it is 503. audit and store reflect the most recent read-log and state-store writes, so they recover after the next successful write.

curl --fail http://127.0.0.1:6480/health
curl --fail http://127.0.0.1:6480/ready
curl --fail http://127.0.0.1:6480/metrics

GET /metrics exposes Prometheus reload counters and the applied timestamp; PostgreSQL routes also expose connection, statement, byte and refusal counters. GET /status reports config and per-route policy reload state. These are operational signals, not an end-to-end readiness guarantee.

Config, policy reload and snapshots

Admin POST /reload and Unix SIGHUP re-read the config file with the same strict loader as startup, then attempt policy files. When policy_watch_ms is set, the config file is also polled with the same two-identical-reads debounce as policy files. A policy-file watch trigger also re-reads the config first. A config error does not block a policy edit, and a policy error does not block a config edit. See the full reloadable and restart-only settings table.

Syntax errors, unknown keys and invalid values reject the whole config reload. Nothing from that config applies. TLS files are loaded before any changes apply. When schemas or search_path changes, a new PostgreSQL catalog snapshot is captured and the route's current policy validated against it. Any failure leaves every route on its last good config and snapshot. Next, [[standing]] is synced to the store; a write failure also rejects the reload. Only then are the remaining settings swapped.

Changed restart-only settings are ignored while reloadable settings apply. Stderr names the setting, never its value:

serve: config reload rejected: <reason>
serve: config reload: restart-only setting <name> changed; ignored until restart

Rejection reasons name keys, never values. Admin GET /status includes this config line:

config revision=<sha256> last_reload=<none|applied|rejected> last_reload_unix_ms=<n> restart_pending=<names|none>

The timestamp is 0 before any attempt. Verify last_reload=applied and the new config revision after editing the config; the 202 response to POST /reload only acknowledges the request. The revision is the SHA-256 of the last applied config file, including when restart-only changes were ignored. Replacing TLS files without editing the config keeps the revision unchanged; verify the new certificate with a new connection.

Management GET /v1/status exposes config_revision, config_last_reload and the config_restart_pending array. Metrics include nunya_config_reloads_total, nunya_config_reload_failures_total and nunya_config_restart_only_ignored{setting="<name>"}. The gauge is 1 while that setting is pending, otherwise 0. Pending names persist until the file matches the running values again or the service restarts. Revert unintended changes and reload, or schedule a restart to apply intended changes. An applied reload does not mean pending settings took effect.

To rotate TLS, replace the certificate and key files in place, then request a reload. Files are re-read even when config text is unchanged. New PostgreSQL, native Spanner and management connections use their new certificates; open connections keep theirs. Adding or removing TLS requires a restart.

Reloads preserve scope salts, tokens, counters and valid sessions. Rotating a standing principal's verifier keeps its principal, sessions and scopes. Removing its [[standing]] entry disables it through the same path as POST /v1/principals/{id}/disable: in-flight work is cancelled, result release stops, connections close and clients receive NY011. Native Spanner RPCs in flight receive NY011; later RPCs receive the uniform NY003. New logins are refused. Removed management administrators are refused on their next request. Names used by API principals cannot become standing principals or management administrators.

Validate an edited policy with nunya policy check before requesting reload. POST /reload and Unix SIGHUP attempt every distinct policy file independently. Files with the same canonical path form one reload unit. Each route validates only its own policy against its own catalog; routes sharing a file reload together after validation against all of their catalogs. A candidate must parse, pass validation and open any permitted changed log sink. A bad edit leaves only the routes on that file on their last good policy; other files are unaffected. The service emits fixed operational reload success/failure diagnostics.

Both routes refresh catalog snapshots periodically. Failed or unsafe snapshots retain the previous snapshot; once it exceeds snapshot_max_age_ms, requests fail with NY008. A reload endpoint response alone cannot establish that the new policy is active. Admin GET /status reports one line per configured route in this format:

route=<id> policy_sha256=<hex> policy_applied_unix_ms=<n> last_reload=<none|applied|rejected> last_reload_unix_ms=<n> policy_watch=<off|ms>

last_reload_unix_ms is 0 before any attempt. Metrics nunya_policy_reloads_total, nunya_policy_reload_failures_total and nunya_policy_applied_unix_ms carry a route="<id>" label. Routes sharing a file report the same numbers. Readiness remains per route. Optional top-level policy_watch_ms watches each file separately and reloads after two consecutive equal changed hashes; rejected bytes are not retried until they change. Unavailable files are skipped, with one diagnostic per unreadable transition.

Connection close after a final error

After a final error, the gateway half-closes the connection and drains input for up to 1.5 seconds or 1 MiB. A client that reads the socket sees NY011. A client that stays idle longer than this window and then writes without reading first may, on Windows, see a connection reset instead: its OS discards the unread error. Retrying on a new connection gets the usual NY003/NY011-style refusals.

Read-log sinks and interpretation

One read-log sink is mandatory for the whole service, covering statement, lifecycle and management records. Version 2 takes [readlog] from service configuration; legacy files may still specify it. All resolved route policies must use the same sink; startup refuses a mismatch with policy files name different read logs. With multiple files, a reload that changes the sink is rejected for that file. To move the log, update all files and restart; a single shared file can still change it on reload. Stdout emits one JSON object per line. File logging appends and flushes each record and rotates to one predecessor with .1 appended. The default file limit is 100 MiB. Parent directories must already exist; relative log paths resolve beside the policy file.

[readlog]
sink = "file"
path = "read.log"
max_bytes = 104857600

The policy reference describes sink, path and max_bytes. Statement records include ts (Unix milliseconds), kind (statement), principal, session, scope, connection, credential_id, route, policy_revision, config_revision, fingerprint, statement, outcome, rows and tokens. The policy_revision is the SHA-256 of the statement route's own policy file. Management session views show their session route's revision. Authenticated management GET /v1/status returns policy_revisions, an object mapping route IDs to revisions (null if unavailable), with the legacy policy_revision field present when one route exists or all routes share one revision, for older clients. config_revision identifies the last applied config file, independently of policy revisions. Identifiers are hexadecimal; no secret or verifier is logged. Lifecycle records cover session issuance, renewal and revocation, principal disablement and refused resumes, each with a fixed, data-free reason. Outcome is allowed or a fixed NY refusal code. Fingerprints are SHA-256 of whitespace-normalised redacted statement text, not semantic query IDs. Explicit tokenize plaintext is removed before hashing.

Logs contain SQL text and released tokens, so restrict access and retention. Ordinary PostgreSQL statements produce an initial intent entry (rows 0) and a later completion entry for simple and extended protocols. Portal suspension may add execution-boundary records. Do not equate entries with unique queries. A sink failure refuses with NY009 and can close the session rather than release unlogged results.

Immediately before returning NY012 on either route, Nunya writes a lifecycle record with kind = lifecycle, event = write_outcome_unknown, ts (Unix milliseconds), principal, session, route, connection, actor = system and reason. The four fixed reasons are revoked, expired, upstream_lost and no_commit_timestamp. It records uncertainty after a forwarded write or COMMIT loses its completion, including session termination, transport loss or a missing Spanner commit timestamp. It contains no SQL text, parameters, row data, tokens or other values. Operators correlate the session, connection, route and timestamp with authorized application and database records to reconcile the outcome before retrying. A failure to write this record emits a fixed diagnostic and still returns NY012; it never changes an unknown outcome into NY009.

Revoking access

Revoke a stored session using its owner credentials, or disable an API-managed principal as an administrator to end all of its sessions:

nunya session revoke --server https://gateway.example:6481 --principal reporting-agent --principal-secret-file principal.secret --context reporting
nunya principal disable reporting-agent --server unix:/var/lib/nunya/nunya.sock

Use a configured administrator over management HTTP on Windows. Config-managed principals must be managed in configuration and cannot be disabled through the API. Grant replacement can reduce access; a reduced grant applies on the next execution.

Revocation and expiry end in-flight work. PostgreSQL cancels the upstream query, relays no further rows, sends one error and closes the connection. NY011 means access session ended. If a write or COMMIT was forwarded before the session ended and completion was not observed, NY012 means write outcome unknown: reconcile the database outcome before retrying. Nothing is replayed. Native Spanner uses PERMISSION_DENIED for NY011 and UNKNOWN for NY012. See errors.

If lifecycle audit is unavailable, revocation and disablement still take effect but return 503 audit_unavailable. Issuance fails closed by revoking the session; renewal returns 503 without changing the session and can be retried with the same idempotency key.

Recovery

Keep state_dir on a local disk only; shared or network directories are unsupported. Run one service per state directory. A second serve using it fails with state is owned by a running service. The durable store is state_dir/nunya.redb. Restrict state, backup and log access as carefully as credentials.

Preserve the root key and private state when upgrading if existing tokens must remain usable. The store checks the root key at startup; a different key stops startup with a continuity-break diagnostic. Replacing it is an explicit continuity break: existing tokens no longer decode. There is no online key rotation, key ring, re-encryption command or backward-key fallback. Generating a key does not rotate a running service. Changing the database behind a route ID also breaks continuity.

Restoring a backup can bring back sessions revoked after that backup. After any restore, revoke all sessions or disable affected principals before serving traffic. Keep database listeners isolated while performing this recovery. An old state_dir/tasks directory is ignored, with one startup notice; it is not migrated into active access sessions.

Qualify policy, schema and driver workflows before upgrading. Ctrl-C or SIGTERM stops accepting and allows up to 30 seconds to drain. Reload to apply standing credentials and management administrators; restart for settings listed in restart-only settings.

Policy management

Policy commands use the same --server, --ca-file, --principal, --principal-secret-file, --context and credential environment variables as principal and session commands. Policy endpoints require an administrator.

nunya policy check --config nunya.toml
nunya policy status <route>
nunya policy effective <route> [--json]
nunya policy validate <route> <file.toml>
nunya policy preview <route> <file.toml> [--json]
nunya policy apply <route> <file.toml> --expected-revision N --catalog-fingerprint F [--idempotency-key K]
nunya policy rollback <route> --to N --expected-revision M [--idempotency-key K]
nunya policy import <route> [--idempotency-key K]
nunya policy revisions <route>
nunya policy revision <route> <n>
nunya policy export <route> [-o file]

Human output contains metadata and counts only. Effective and preview --json output contains the server projection. Preview prints its catalog fingerprint; apply requires that fingerprint via --catalog-fingerprint. Mutations print their retry key; retain and reuse it for retries. A stale apply prints the current revision and diff counts and exits nonzero.

The base endpoint is /v1/routes/{route}/policy (GET status). GET suffixes are /effective, /revisions, /revisions/{n} and /export. POST /validate and /preview accept {policy_toml}; /apply additionally requires expected_revision and catalog_fingerprint. POST /rollback accepts {to,expected_revision}; POST /import accepts an empty object. Mutations require the Idempotency-Key header. Success returns a revision summary and replay flag; 409 stale_revision includes current and diff, and 409 catalog_changed includes the current fingerprint. Invalid drafts return 422; unavailable policy or audit storage returns 503.

Import transfers a file-owned route to service ownership. To return it explicitly to file ownership, export first:

nunya policy export <route> -o policy.toml

Point that route's policy setting at the exported file, set policy_owner = "file" in its [upstream] or [spanner_native] section, and restart. Ownership changes only at startup; hot reload requires a restart for this setting. All revisions remain available. Before importing again, remove the key and restart, then import. Import refuses with 409 file_owner_configured while the key remains configured. Status reports durable active_revision and actually enforced published_revision (or null); a mismatch requires a retry or restart. The policy revision tables are new in this release. An older binary using the same state directory ignores service ownership and serves the policy file. Do not downgrade a deployment with service-owned routes.

For a single replica, policy apply reports pending while connections are still releasing rows checked under the previous revision. Policy status shows the pending statement count and becomes active once those releases finish. Per-batch fencing on any tightening stops further result release by every open statement on that route, including statements unaffected by the changed columns, with NY008; loosening lets statements finish under their original policy. Active means every row checked under the old revision has been handed to the transport: the PostgreSQL socket write has returned, tonic has taken a Spanner stream part, or a Spanner unary ExecuteSql/Read response has been checked immediately before return to tonic. This acknowledgement applies only to the current replica.

Kubernetes policy store (preview)

In peer mode, each pod has its management socket at <state_dir>/pods/<pod_name>/nunya.sock; pass it to the CLI with --server unix:<path>.

Build with --features kubernetes, set policy_store = "kubernetes", and configure [policy_store_kubernetes] with namespace, pod_name and this pod's management_url (an http/https base URL without path or userinfo). These settings require a restart. Without the feature, config loading refuses this backend. The default backend remains local.

The namespaced NunyaPolicy CRD holds the active head. Writes use Kubernetes resourceVersion compare-and-swap; competing updates refuse rather than overwrite. NunyaPolicyRevision objects retain history. A service-owned route loads its active revision before serving and refuses startup if that revision cannot be loaded. The client uses in-cluster credentials, falling back to kubeconfig.

A coordination Lease elects the policy writer. Defaults are lease_name = "nunya-leader", lease_duration_secs = 15, renew_deadline_secs = 10, and retry_period_secs = 2; require 0 < retry < renewal deadline < lease duration. An expired local renewal fences writes; graceful shutdown releases the Lease. Network requests to non-leaders return HTTP 307 to the observed leader management URL, or HTTP 503 no_leader when none is known. Local Unix administration stays on that pod. Clients refuse redirects by default and report the leader URL. Opt in with --follow-leader to follow once, only from HTTPS to HTTPS using the original TLS roots/--ca-file. Every advertised endpoint must be trusted by that configuration. Expiry uses unchanged Lease observations measured by a monotonic clock, regardless of remote wall time. Each API call, including shutdown release, times out after five seconds.

Apply the CRDs, namespace Role/ServiceAccount/RoleBinding, then the preview ConfigMap/Deployment from deploy/kubernetes/. The Role grants only policy get/create/update, history get/list/create and Lease get/list/create/update. Dynamic per-pod Lease names require namespace-scoped access; create cannot be name-scoped and is needed on first start. No delete, patch, watch, secrets, pods or cluster-wide rights are granted. The deployment renders plain pod name and management URL strings from the downward API; config has no general env:NAME expansion.

Each pod holds nunya-serving-<pod_name>. Restart-only keys in [policy_store_kubernetes] default to serving_lease_secs = 6, serving_renew_interval_ms = 1000 and serving_margin_ms = 1000. The margin must leave more than two renewal intervals inside the term. Each renewal cycle has a total budget of term minus margin minus renewal interval; every API call, including head adoption, is bounded by the remaining budget, and an over-budget cycle never extends the gate. File-owned routes confirm revision zero and keep their file policy. Pods poll the active heads at each renewal, adopt revisions locally, write their confirmation and re-read heads before extending their gate. After restart a pod refuses serving until it has loaded the active revision and holds a serving lease.

A pod that cannot renew within the term refuses new connections and stops releasing rows with PostgreSQL NY013 or Spanner UNAVAILABLE. The gate closes at term minus margin measured from the renewal request start. An API-server outage longer than one term therefore stops serving on every pod: fail closed. Expiration and leadership use monotonic clocks; clock rate drift must stay below margin/term. No wall-clock offset assumption is needed.

Apply and rollback wait at most two seconds, then return pending or active with per-pod progress. A tightened revision is active when every live serving pod confirms it (older release slots have finished), or when each non-confirming pod's unchanged Lease has expired on the leader's monotonic clock. A loosened or identical revision is active once written only if no earlier revision on that route is still pending; otherwise every live pod must confirm the new revision or expire. A new leader treats every observed Lease as live for at least one full serving term; deleted Leases are dropped. Status reports loaded and confirmed revisions, gate state, and on the leader each pod's confirmation, live/expired state and elapsed time since resourceVersion changed. Followers report activation as unknown with reason "leader owns activation", alongside local progress. Each observed Lease remains live for the greater of the leader serving term and its own positive leaseDurationSeconds; missing or invalid durations never expire. A holder identity that differs from the pod suffix cannot confirm a revision.

Multi-replica serving is supported only in this one-node topology. All three replicas run on one node with required co-location and mount one ReadWriteOnce PVC holding state_dir, using local-path or a block CSI volume, with [kubernetes.peer] configured. The peer state API serves sessions, scopes, revocation feeds and counter batches from the leader, cached by pods under their serving lease. Do not use ReadWriteOncePod, NFS or ReadWriteMany: the store relies on an exclusive file lock (flock). Only the leader-Lease holder opens the state store; followers never open it. A new leader opens it after the old process releases the lock. A force-killed pod released it within about 0.1 seconds in the kind test. A running pod holds it until it notices Lease loss at the renew deadline; a frozen old leader blocks failover until killed, failing closed. Losing the node is an outage until the node or its volume returns. Replicas provide process failover and support rolling restarts, with no node high availability. Peer request bodies are authenticated but not encrypted (responses are sealed), so the peer port 6482 must stay on the pod network behind a NetworkPolicy. NetworkPolicy requires an enforcing CNI; kindnet does not enforce it.

The repository manifest in deploy/kubernetes/ defaults to three replicas. The live kind + Calico v3.31.2 proof with the --features kubernetes image kept all three Ready together, including followers started before policy import. A leader-issued session worked on every pod with identical tokens; revocation reached every pod in under one second, within one serving-lease term; and the per-principal tokenize limit held across pods (exactly the limit, then NY007). Leader force-delete handed over in about 17 seconds with sessions, tokens and counters retained. A tightened apply stopped a follower cursor with NY008 before it was reported active. An API-partitioned pod returned NY013 and /ready 503; a restarted pod served only the current revision. NetworkPolicy blocked 6482 from non-Nunya pods and kept admin 6480 closed. See harness/k8s/ for re-running the proof.

When upgrading from 8a, restart all pods together: 8a pods have no serving Lease and are invisible to activation. Every pod must serve the same set of routes. Set pod_name uniquely per pod using the downward API. Install Nunya in its own namespace because the Role grants Lease permissions throughout that namespace.
