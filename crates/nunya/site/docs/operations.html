Operations

Run Nunya as a dedicated unprivileged service with private configuration, writable state and a read log. Keep the database network and credentials inaccessible to the agent.

Container and service layout

docker build -f crates/nunya/Dockerfile -t nunya .

Run that build from the repository root. The multi-stage Dockerfile builds the release binary on rust:1-bookworm with clang/libclang-dev, then copies it into debian:bookworm-slim. It runs as uid/gid 10001 and exposes 6432. Its default command is serve --config /etc/nunya/nunya.toml. This page documents the recipe; it does not claim a published registry image.

docker run --rm --name nunya \
  -p 127.0.0.1:6432:6432 \
  --mount type=bind,src=/absolute/private/config,dst=/etc/nunya,readonly \
  --mount type=bind,src=/absolute/private/state,dst=/var/lib/nunya \
  nunya

Replace both absolute host paths. In the mounted configuration, set state_dir to /var/lib/nunya, listen to 0.0.0.0:6432 so Docker can forward to it, and upstream host to an address reachable from the container. Container loopback is not the host database. Pre-create the state directory owned by uid 10001 and mount root-key, password and TLS files read-only with permissions that uid can read. Keep admin private; the example does not publish its port.

For a host service use a dedicated account and run nunya serve --config /etc/nunya/nunya.toml. Configuration/service errors exit 1; clean shutdown exits 0.

TLS and secrets

Inbound [tls] requires cert_file and key_file. Without it, explicit allow_plaintext = true is required. Both routes share these files. Keep private keys and root keys out of source control, errors and shell history. Relative file paths are resolved beside the configuration.

For PostgreSQL upstream upstream.tls, disable is plaintext; require encrypts but accepts any certificate; verify-full checks the hostname using ca_file as the only trust root. Configure the agent client to verify the inbound server certificate as well. These are separate TLS connections.

[tls]
cert_file = "server-chain.pem"
key_file = "server-key.pem"

[upstream]
host = "db.internal"
port = 5432
user = "nunya"
dbname = "app"
password_file = "upstream.password"
tls = "verify-full"
ca_file = "database-ca.pem"

The fragment must be combined with a complete top-level configuration and policy. root_key_file and password_file take precedence over their environment alternatives, NUNYA_ROOT_KEY and NUNYA_UPSTREAM_PASSWORD.

Admin listener

The PostgreSQL route starts the unauthenticated HTTP admin listener, default 127.0.0.1:6480 via admin_listen. A native-only service starts no admin listener. Keep it loopback or on a tightly controlled management network.

RequestMeaning
GET /health200 with body ok; this is a basic endpoint response, not an upstream-query readiness proof.
GET /metricsPrometheus text counters for connections, allowed statements, bytes and each NY refusal code.
POST /reload202 means the reload signal was queued, not that validation succeeded; 503 means the queue is unavailable.
curl --fail http://127.0.0.1:6480/health
curl --fail http://127.0.0.1:6480/metrics
curl --fail -X POST http://127.0.0.1:6480/reload

The bounded listener accepts HTTP/1.1, requires Host, closes after one request, limits the total request to 8192 bytes and uses a five-second read timeout. It has no authentication or TLS of its own. Do not expose it to agents or the public network.

Policy reload and snapshots

Validate an edited policy with nunya policy check before requesting reload. POST /reload and Unix SIGHUP reload the PostgreSQL route only. The candidate policy must parse, validate against the current snapshot and open its log sink; failure retains the current policy. The service emits fixed operational reload success/failure diagnostics.

The native Spanner route retains its own policy and needs restart for policy changes, even when running beside PostgreSQL. Both routes refresh catalog snapshots periodically. Failed or unsafe snapshots retain the previous snapshot; once it exceeds snapshot_max_age_ms, requests fail with NY008. A reload endpoint response alone cannot establish that the new policy is active.

Read-log sinks and interpretation

A read-log sink is mandatory. Stdout emits one JSON object per line. File logging appends and flushes each record and rotates to one predecessor with .1 appended. The default file limit is 100 MiB. Parent directories must already exist; relative log paths resolve beside the policy file.

[readlog]
sink = "file"
path = "read.log"
max_bytes = 104857600

The policy reference describes sink, path and max_bytes. Records contain ts (Unix milliseconds), task, credential, fingerprint, statement, outcome, rows and tokens. Outcome is allowed or a fixed NY refusal code. Fingerprints are SHA-256 of whitespace-normalised redacted statement text, not semantic query IDs. Explicit tokenize plaintext is removed before hashing.

Logs contain SQL text and released tokens, so restrict access and retention. Ordinary PostgreSQL statements produce an initial intent entry (rows 0) and a later completion entry for simple and extended protocols. Portal suspension may add execution-boundary records. Do not equate entries with unique queries. A sink failure refuses with NY009 and can close the session rather than release unlogged results.

Tasks, standing identities and revocation

nunya task open creates persistent task scope state and prints its secret once. Protect the state directory; it contains authentication material and tokenization counters. task list does not reveal secrets. nunya standing hash reads one password line from standard input and emits a SCRAM verifier; protect that verifier as a credential.

Closing or expiring a task prevents new PostgreSQL authentication, but does not terminate already authenticated PostgreSQL sessions: those retain scope keys. Explicit task tokenization checks the live task counter. For immediate isolation, also terminate affected connections at your service/network layer. Native Spanner authentication revalidates a task on every RPC, including cache hits. Standing credentials do not carry task TTLs.

Changing keys and upgrading

There is no key-rotation command, key ring, online re-encryption workflow or backward-key fallback. nunya key generate emits a new root key; it does not rotate a running service. Root keys are loaded at startup and scope keys are derived from them. Plan a controlled restart and new task/token lifecycle if replacing the key: do not expect old issued tokens to work with a different root.

Preserve private state and the existing key when upgrading a binary if existing task tokens must remain usable. Qualify policy, schema and driver workflows before changing a deployment. Ctrl-C or SIGTERM stops accepting PostgreSQL connections and permits sessions up to 30 seconds to drain. Restart native routes to apply policy or credential configuration changes. Keep backups and logs under the same access controls as the live service.
