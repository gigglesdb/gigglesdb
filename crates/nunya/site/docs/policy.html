File structure and defaults

Policy TOML rejects unknown keys at every level and collects independent validation errors. Unlisted columns are plain: protect every sensitive column explicitly. The read-log table is required; domain and column collections may be omitted and then are empty. Each route selects a policy using its own configuration key or the optional service-level fallback. Parsing is followed by validation against that route's captured catalog; a protected column need not exist on another route. See policy file selection.

Read-log keys

Under [readlog], configure the audit destination before starting the gateway. Relative path resolves against the directory of the policy file as named in the config (not a symlink's target), and two policies naming the same log file by different spellings are accepted. There is one read log for statement, lifecycle and management records. Every policy file must name the same sink; startup refuses a mismatch with policy files name different read logs. With several files, a reload that changes [readlog] is rejected for that file. To move the log, update all files and restart. With a single shared file, reload can still change the sink.

KeyType / defaultMeaning and validation
sinkstring; requiredExactly stdout or file. No implicit valid sink is supplied when the table or key is missing.
pathstring; omittedRequired and nonempty for file. Parsed but unused for stdout.
max_bytespositive integer; 104857600File rotation threshold (100 MiB). Zero and negative values are invalid, including when sink is stdout.
[readlog]
sink = "file"
path = "read.log"
max_bytes = 104857600

A read-log failure prevents database work from proceeding. Logs may contain SQL and tokens; restrict their permissions. See operations.

Domain keys

Write each domain as [domains.email], substituting your domain name. Names contain 1-31 ASCII bytes, start with a lowercase letter, and otherwise contain lowercase letters, digits or underscores. A declared domain may be unused.

KeyType / defaultMeaning and validation
tokenizestring; "off"Exactly off or on. Enabling allows explicit token creation from supplied plaintext; it does not change ordinary protected-column tokenization.
tokenize_limit_per_sessioninteger; 1 through 100000; no defaultRequired when tokenize is on; rejected when off. See Tokenization limits.
tokenize_limit_per_principalinteger; 1 through 100000000; no defaultRequired when tokenize is on; rejected when off. See Tokenization limits.
tokenize_principal_windowduration string; 1m through 31d inclusive; no defaultRequired when tokenize is on; rejected when off. See Tokenization limits.
rangetable; omittedOptional inclusive numeric interval. Without it the token codec uses the type's default range. Both endpoints are mandatory when present.
minsigned 64-bit integer; required in rangeInclusive lower bound; must not exceed max.
maxsigned 64-bit integer; required in rangeInclusive upper bound. Schema validation requires at least 1048576 distinct values and an interval fitting every participating type.
[domains.account_id]
tokenize = "off"
range = { min = 0, max = 1048575 }

The range example suits an integer domain with enough representable values. It is not valid for text or UUID domains. Date bounds are PostgreSQL epoch-relative days, from -730119 through 2921939 (Gregorian years 0001-9999). Timestamp and timestamptz bounds are epoch-relative microseconds from -730119 * 86400000000 through 2921940 * 86400000000 - 1. These numbers configure the codec; they are not a filter on query results.

Tokenization limits

All three settings are required with tokenize = "on" and rejected when off (including the default off). The principal limit must be at least the session limit. The window uses a positive decimal integer with one lowercase s, m, h or d suffix; fractions, spaces, zero and overflow are refused. Unknown keys are rejected.

The per-session counter covers explicit plaintext tokenization in this domain for one access session. The per-principal counter is keyed by principal and domain name and combines that principal's sessions across routes that use the same domain name. Each route enforces its own domain limit against the shared count, even when the files define different limits. The length of a principal window is set by whichever route opens it. A session belongs to one route, so its per-session counter stays with that session. Use different domain names to keep routes' counters independent. The principal counter's fixed-length window starts at the first tokenization after the preceding window ended. Restart, reconnect or a new session cannot reset it. Either exhausted limit refuses with NY007; ordinary protected SELECT output is separate.

Reloaded limit changes apply on the next tokenization and never clear counters. Lowering a limit can immediately refuse further creation; starting another session does not evade the principal limit.

Column keys

Each entry has exactly one treatment. Masking substitutes a string or SQL NULL; blinding preserves an approved token flow.

KeyType / defaultMeaning and validation
tablestring; requiredSchema-qualified table name with exactly one dot and a nonempty table component. For the native Spanner default schema use .Customers, including the leading dot.
namestring; requiredColumn name. The referenced column must exist in the captured schema.
blindstring; absentNames a declared domain. Cannot coexist with masked, even masked = false.
maskedboolean; absentWhen supplied it must be true. Cannot coexist with blind.
placeholderstring; omitted means SQL NULLAllowed only for masked treatment. A string placeholder requires a textual column; omit it for a non-textual masked column.
[[column]]
table = "public.customers"
name = "phone"
masked = true
# Omit placeholder to return SQL NULL.

Schema validation and safe rollout

Protected columns must belong to a Table relation, not a view. Blind types supported are text, varchar, bpchar, int4, int8, UUID, date, timestamp and timestamptz. Textual types share one family; all other types must match within a domain. int2 has too few values for safe encryption; boolean and enums must be masked. Numeric, bytea, JSON, JSONB, arrays and unknown types are refused for blinding.

Triggers, rules, row policies, generated columns and defaults that read a blind or masked column make the policy unsafe: Nunya cannot inspect what those objects copy. Views are skipped by this dependent-object validation, but a protected policy column itself still must be on a table. Resolve the dependent object rather than weakening the protection.

nunya policy check --config nunya.toml

This command loads credentials, opens the read-log sink, connects to every configured catalog, and validates each route's own policy only against its own snapshot. It is more than a syntax checker. On success its fixed output is:

policy OK

After a successful check, request reload through the private admin endpoint or Unix SIGHUP, or enable top-level policy_watch_ms for every file. Each distinct canonical policy path is one reload unit, attempted independently. A rejected file leaves only its routes on their last good policy; other files are unaffected. Routes sharing a file reload together after validation against all of their catalogs. GET /status reports one line per route with its applied policy hash and latest reload outcome. The route's policy_revision is the SHA-256 of its own file; statement records and management session views use that route's revision. Management GET /v1/status returns policy_revisions (route ID to revision, null if unavailable), with the legacy policy_revision field present when one route exists or all routes share one revision; config_revision is unchanged. See operations.
