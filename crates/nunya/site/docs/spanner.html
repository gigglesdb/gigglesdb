Spanner

Nunya has two Spanner routes: a PostgreSQL connection through PGAdapter and a native GoogleSQL gRPC listener.

Choose the route

RouteAgent connectionUpstream
PostgreSQL / PGAdapterPostgreSQL driver, SCRAM user and secretPGAdapter serving a PostgreSQL-dialect Spanner database
Native GoogleSQLSpanner gRPC client with Nunya bearer metadataSpanner database resource using GoogleSQL

At least one route is required. Both may run in the same process with the same policy, root key, task store, standing identities and inbound certificate/key files. policy check validates the policy against every configured catalog. Policies must name the actual case-sensitive native schema/table/column names. For a default-schema GoogleSQL table use the leading-dot spelling, for example table = ".Customers".

Start the emulator harness

From crates/nunya, with Docker Compose, Bash, curl and Python 3 available, run:

bash harness/run.sh spanner

The script prints its fresh temporary task root. Use --task-root /path/to/runs to choose another directory. Keep the terminal open. Compose exposes emulator gRPC on 127.0.0.1:9010, REST on 127.0.0.1:9020 and PGAdapter on 127.0.0.1:5432. The setup script creates test-instance and two seeded databases, gsql and pgdb. The harness prints these test environment values:

export NUNYA_TEST_SPANNER_EMULATOR=127.0.0.1:9010
export NUNYA_TEST_SPANNER_DB=projects/test-project/instances/test-instance/databases/gsql
export NUNYA_TEST_SPANNER_PGADAPTER=127.0.0.1:5432

These variables identify upstreams for the repository tests; they do not configure a running gateway. The compose images are emulator 1.5.41 and PGAdapter v0.56.1. Press Enter to stop and remove that run's containers and volumes.

PostgreSQL route through PGAdapter

Start with the quickstart configuration. In its upstream section choose upstream.dialect = "spanner-pg", change port to 5432 and database to pgdb. Keep the harness credentials isolated. The PGAdapter container uses emulator auto-configuration; it is not a production credential recipe.

[upstream]
dialect = "spanner-pg"
host = "127.0.0.1"
port = 5432
user = "nunya"
dbname = "pgdb"
tls = "disable"
connect_timeout_ms = 5000
application_name = "nunya"

Use the lowercase PostgreSQL harness policy (harness/policy.toml) and supply the root key and upstream password as in the quickstart. Run policy check, open a task, then serve. The agent still connects to Nunya on port 6432 using a PostgreSQL driver. Catalog loading uses the Spanner PostgreSQL dialect.

Native listener configuration

Create a private configuration directory. Copy harness/spanner/policy_gsql.toml there as policy.toml, generate a root key, and use this local-only configuration:

policy = "policy.toml"
state_dir = "state"
root_key_file = "root.key"
allow_plaintext = true

[spanner_native]
listen = "127.0.0.1:6433"
database = "projects/test-project/instances/test-instance/databases/gsql"
emulator_endpoint = "http://127.0.0.1:9010"
snapshot_refresh_ms = 30000
umask 077
export NUNYA_SPANNER_DIR=$(mktemp -d)
mkdir -p "$NUNYA_SPANNER_DIR/config/state"
cp harness/spanner/policy_gsql.toml "$NUNYA_SPANNER_DIR/config/policy.toml"
nunya key generate > "$NUNYA_SPANNER_DIR/config/root.key"
# Save the configuration above as "$NUNYA_SPANNER_DIR/config/nunya.toml".
nunya policy check --config "$NUNYA_SPANNER_DIR/config/nunya.toml"
nunya task open --config "$NUNYA_SPANNER_DIR/config/nunya.toml" --ttl 30m
nunya serve --config "$NUNYA_SPANNER_DIR/config/nunya.toml"

A native-only configuration omits top-level listen and [upstream]. There is no admin listener in this mode. spanner_native snapshots refresh periodically (default 30000 ms); failed or policy-invalid snapshots leave the previous snapshot in place. Changing this route's policy requires a restart.

Bearer credentials and token parameters

Every agent RPC supplies exactly one authorization metadata header. The value is case-sensitive:

Authorization: Bearer nunya.task:REPLACE_WITH_ID.REPLACE_WITH_SECRET

For a standing identity, replace task:ID with its configured name. Parsing splits the first separator after the user and preserves dots in the secret. Missing, duplicate, malformed or invalid credentials fail uniformly. Task close and expiry are checked on every native authentication, including cache hits. Standing scopes last for the process lifetime; PostgreSQL standing scopes are per connection.

Bind a token as a named query parameter and declare its appropriate Spanner type. GoogleSQL token literals are never decrypted. An illustrative ExecuteSql payload fragment is:

{
  "sql": "SELECT Id FROM Customers WHERE Email = @email",
  "params": {"email": "REPLACE_WITH_TOKEN_FROM_THIS_TASK"},
  "paramTypes": {"email": {"code": "STRING"}}
}

The fragment omits the session and transaction selectors your client must supply. Carry the token unchanged; do not put it in SQL text. Token detection does not recurse into ARRAY/STRUCT parameters.

Explicit tokenization on the native route

A standalone SELECT nunya_tokenize('email', @value) explicitly tokenizes known plaintext for a domain. The value may also be a plain quoted string literal. Aliases, including backtick aliases, are refused with NY004; the result column is always nunya_tokenize. The call cannot be combined with FROM, WHERE, GROUP BY, HAVING, QUALIFY, WINDOW, WITH, ORDER BY, LIMIT/OFFSET, DISTINCT, SELECT AS STRUCT/AS VALUE, a set operation or another select item. It cannot appear inside another expression, subquery, CTE, view or DML. These uses are refused with NY004.

The function name must be unqualified and is case-insensitive like other GoogleSQL function names; backtick quoting is allowed. nunya.nunya_tokenize is refused on this route because a qualified GoogleSQL function name refers to a function in a named schema. The PostgreSQL route also accepts the nunya. form. The domain argument must be a single- or double-quoted string literal naming the domain exactly.

Prefer a named query parameter for the plaintext. Literals must be plain 'value' or "value" strings. Doubled delimiters (such as 'a''b' or "a""b"), embedded newlines and carriage returns are refused in both domain and value literals. Raw, bytes and triple-quoted literals are refused, and any backslash in the statement text refuses the call with NY004, because escape decoding must not differ from Spanner's. Numbers, NULL and typed literals are refused.

The result has the type of the domain's blind column: STRING, INT64, DATE or TIMESTAMP. A literal or untyped parameter is read as that type; a parameter declared with a different type (non-string versus string) is refused with NY004. The token equals the token this access session receives when it reads the same value from a blind column of that domain, so it can be bound as a query parameter like any other token.

Nunya answers the call without contacting Spanner. The session must be admitted and the domain must enable tokenize. The persisted per-session and per-principal limits share the PostgreSQL route's counting rules and survive reconnects, credential rotation, re-acquisition and restarts. Exhaustion is NY007 (PermissionDenied). After counting, Nunya re-checks the session; a session revoked at that moment gets NY011 and no token. Every refusal is written to the read log as a refused record with the fixed label, never the plaintext.

A NULL parameter is refused with NY004 and costs no count. nunya_tokenize cannot be the statement that begins a transaction: a begin selector, or a single-use read-write or partitioned-DML selector, is refused with NY004. Run it with no selector, a single-use read-only selector, or inside an existing transaction by id.

A request that carries a resume_token is refused with NY004, so a resumed stream never counts twice. Inside ExecuteBatchDml it is refused with NY004.

An illustrative ExecuteSql payload fragment is:

{
  "sql": "SELECT nunya_tokenize('email', @v)",
  "params": {"v": "carol@example.test"},
  "paramTypes": {"v": {"code": "STRING"}}
}

RPC surface and refusals

The native proxy implements session creation/batch creation, get/list/delete, ExecuteSql, ExecuteStreamingSql, ExecuteBatchDml, Read, StreamingRead, BeginTransaction, Commit and Rollback. Sessions are tied to the authenticated principal. Mutations and structured reads are lowered and checked before forwarding; streaming values are reassembled before blind output is tokenized.

PartitionQuery, PartitionRead and BatchWrite are refused. Index reads (a non-empty index field) are refused. Partition tokens, data boost and non-default query modes are rejected. Unsupported structured operations fail closed; supported RPC names do not imply every option or SQL shape is allowed.

Native refusal statuses include the NY code in a fixed message. NY004 maps to gRPC InvalidArgument; NY008 and NY009 map to FailedPrecondition; NY012 maps to Unknown; NY011 maps to PermissionDenied; all other NY refusals (including NY007) map to PermissionDenied. Upstream status codes are retained with fixed messages and cleared details/metadata.

Production configuration boundary

Without emulator_endpoint, native upstreams use Google credentials and HTTPS. The default upstream endpoint is https://spanner.googleapis.com; endpoint may select a trusted HTTPS endpoint. Emulator mode requires an explicit http:// emulator endpoint and does not obtain Google credentials. Do not use this local plaintext example for an exposed service: configure inbound TLS, isolate the upstream, protect state and credentials.
