Quickstart

Deploy the gateway once, provision an identity, then connect with an access session. Your application keeps its direct database connection.

On this page

  • Cleanup

1. Deploy once

Have the Nunya binary and psql available. To build from source, run cargo build --release from crates/nunya and put the release binary on PATH. For a local database, run bash harness/run.sh --work-root /path/to/private/work (choose a private work directory for your machine) in another terminal from that directory. It starts PostgreSQL 16, 17 and 18 on loopback ports 16432, 17432 and 18432 and seeds the app database. Keep that terminal open. Its public test password is only for isolated local development. This is the default PostgreSQL mode; bash harness/run.sh private --work-root /path/to/private/work runs the separate private harness and requires a Nunya binary. The examples below use the default mode.

In a private directory, save this as nunya.toml and copy harness/policy.toml beside it. Create the private state directory first. The policy blinds email addresses, masks phone numbers and leaves country and payment counts plain. Review it before exposing another schema.

listen = "127.0.0.1:6432"
admin_listen = "127.0.0.1:6480"
policy = "policy.toml"
state_dir = "state"
root_key_file = "root.key"
allow_plaintext = true

[upstream]
host = "127.0.0.1"
port = 16432
user = "nunya"
dbname = "app"
password_file = "upstream.password"
tls = "disable"

[management]
listen = "127.0.0.1:6481"

From that private directory, generate the root key and write the harness password. These shell commands use Bash; Windows users can create the same files with private profile ACLs.

umask 077
mkdir -p state
nunya key generate > root.key
printf '%s\n' 'nunya-harness-only' > upstream.password
nunya policy check --config nunya.toml
nunya serve --config nunya.toml

Keep serve running, and use another trusted terminal for provisioning and connections. Loopback and explicit plaintext are for this local example. Use verified TLS for remote traffic, including TLS on management outside loopback. See configuration and policy reference. Consult reload and restart rules when changing configuration.

2. Provision an identity

On Unix, run these commands as the service user through state_dir/nunya.sock. Replace the example absolute path with your private state directory. This mode-0600 socket grants administrator authority. Create an agent principal, give it a grant on route postgres, then add a credential.

nunya principal create reporting-agent --kind agent --server unix:/absolute/private/state/nunya.sock
nunya principal grant reporting-agent --route postgres=read-only --server unix:/absolute/private/state/nunya.sock
nunya principal credential add reporting-agent --generate-secret --server unix:/absolute/private/state/nunya.sock

The last command prints a credential ID followed by a one-time secret. Save only the secret line as principal.secret in a private file; it cannot be displayed again. Do not give the agent administrator access or the upstream password.

Windows has no Unix socket. Before starting the service, run nunya standing hash, enter a private administrator password on stdin, and put its generated verifier in this configuration entry. The command generates a verifier; it does not create a database login.

[[management.admin]]
name = "operator"
verifier = "REPLACE_WITH_GENERATED_SCRAM_VERIFIER"

Save the original administrator password as the first line of private operator.secret. With the entry loaded by serve, use these commands instead of the Unix provisioning commands:

nunya principal create reporting-agent --kind agent --server http://127.0.0.1:6481 --principal operator --principal-secret-file operator.secret
nunya principal grant reporting-agent --route postgres=read-only --server http://127.0.0.1:6481 --principal operator --principal-secret-file operator.secret
nunya principal credential add reporting-agent --generate-secret --server http://127.0.0.1:6481 --principal operator --principal-secret-file operator.secret

Save the one-time agent secret in principal.secret. See principal commands for credential expiry and grant replacement.

3. Connect

Use the agent principal on the management API to acquire a session. These commands work on Unix and Windows; keep server, principal and context identical to resume the same token scope.

nunya session acquire --server http://127.0.0.1:6481 --principal reporting-agent --principal-secret-file principal.secret --route postgres --context reporting --ttl 1h
nunya exec --server http://127.0.0.1:6481 --principal reporting-agent --principal-secret-file principal.secret --context reporting -- psql -d app -c "SELECT id, email, phone FROM customers ORDER BY id"

The helper supplies PostgreSQL environment credentials to psql. The database username is session:REPLACE_WITH_SESSION_ID (an actual ID is 32 lowercase hex characters) and its password is the session secret. Principal credentials never authenticate on a database port. Emails arrive as tokens valid within the session's token scope; phones arrive as placeholders. The read-only grant refuses writes.

For another driver, nunya session env prints the stored PostgreSQL environment. Use --format sh or --format powershell for your shell, and treat the output as secret.

nunya session env --server http://127.0.0.1:6481 --principal reporting-agent --principal-secret-file principal.secret --context reporting --format sh

Reconnecting to the same active session and renewing preserve the scope and keep its tokens usable. A new isolated scope does not share token equality or validity. Renewal refreshes last-used time, not absolute expiry. If the stored session has ended, the helper refuses replacement until you explicitly use --new-scope; obtain fresh tokens for that new scope. Protect the helper's private sessions.json under its per-user state directory, overridable with NUNYA_HOME. Launch an agent with nunya exec so credentials stay out of its prompt. See session commands and concepts. Follow the end-to-end walkthrough to reuse a token after reconnecting; consult drivers for supported driver metadata statements.

Cleanup

While the service is still running, revoke the access session:

nunya session revoke --server http://127.0.0.1:6481 --principal reporting-agent --principal-secret-file principal.secret --context reporting

Revocation ends active work; see NY011 and NY012 for interrupted queries and unknown write outcomes. Stop the foreground service with Ctrl-C. Press Enter in the harness terminal to remove its containers and volumes. Protect or remove the private demonstration credentials, configuration and state when finished.
