Follow the query, not the secret

Where Nunya fits

Nunya is a separate entry point for AI agents; applications keep their existing direct database connections. Agents use their own endpoint and access-session credentials, while Nunya connects upstream with its own least-privilege role configured by [upstream] user. PostgreSQL agents use ordinary drivers.

The request path

The database keeps its ordinary stored values. Principals authenticate only to the management API to acquire access sessions within their route grants. The database ports accept session credentials: PostgreSQL uses session:REPLACE_WITH_SESSION_ID and the session secret; native Spanner uses nunya.session:REPLACE_WITH_SESSION_ID.REPLACE_WITH_SESSION_SECRET as its bearer. Nunya uses a separate upstream connection.

1. Parse and resolve against a snapshot

Before SQL analysis, database authentication looks up the access session and its stored scope. The root key, deployment ID, route ID and persisted random salt derive its token keys. Execution revalidates session liveness and effective grants; revocation or expiry stops active result release. Reconnects and renewals retain the scope. The local durable state store, state_dir/nunya.redb, preserves principals, grants, sessions, scopes and explicit tokenization counters across restarts. Preserve both it and the root key for continuity.

The dialect parser turns a statement into a representation whose column uses, inputs, writes and outputs can be inspected. Column names are resolved against the schema snapshot and search path. A name alone cannot establish the type or protection of a value.

Analysis must cover the statement. Unknown or unsupported forms are refused rather than forwarded unchecked. Policy validation checks the actual schema, column types and unsafe dependent objects. An unsafe or failed snapshot refresh retains the old snapshot; a stale snapshot ultimately causes NY008 refusals.

2. Check uses against the policy

A blind column may be returned as a token, compared for equality in permitted contexts, grouped, counted or checked for NULL. A same-domain equality join can work without exposing the value. Pattern matching, ordering, arithmetic and arbitrary functions on a blind value are refused.

Masked columns may be returned as their configured placeholder or SQL NULL. Using one as an expression is refused. Plain columns support ordinary analysed SQL, but a recognized token cannot be used to move a blind value into an unrelated plain destination. Review the token-detection edge cases in Limitations.

3. Rewrite only approved inputs

The checker produces a plan describing which inputs need decoding. A token in a permitted position is decoded using the current scope and domain, then the rewritten statement or bound parameters go upstream. A token does not carry blanket authority to decrypt itself anywhere in SQL.

SELECT id, country FROM customers WHERE email = %s

In the recorded lookup, the email token is the bound parameter. The agent gets customer id 3 and country US. On native GoogleSQL, always pass tokens as query parameters: GoogleSQL literals are never decrypted.

4. Re-tokenize and log the result

Blind result columns become typed tokens. Masked outputs become placeholders or SQL NULL. Ordinary outputs retain their values. Result-shape and type checks prevent an unexpected upstream response from silently bypassing the plan.

The read log records outcomes, rows and released tokens. Explicit tokenize arguments are redacted before statement logging and fingerprinting. Log failures are refusals. Ordinary forwarded PostgreSQL statements can have an initial rows=0 intent record and a completion record. Logs can contain query text and tokens; keep them private.

A permitted action and a refused action

Each route can use a separate policy file, with a top-level fallback and one shared read-log sink. PostgreSQL and native Spanner policy contents reload after validation. Selected settings such as certificates reload too; listener addresses, policy paths, root key, route IDs and state directory need restart. See reload boundaries.

The reminder succeeds because customers.email and outbox.to_address share the email domain. Copying the token to notes.body fails with NY001. Probing email with LIKE fails with NY002. The walkthrough shows exact inputs, outputs and stored rows.
