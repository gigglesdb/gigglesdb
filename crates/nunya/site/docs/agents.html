Agent instructions

A ready-made excerpt for CLAUDE.md, AGENTS.md or a system prompt. It tells an AI agent how to connect through Nunya, what tokens are, which queries work on protected columns, and what to do when a query is refused.

Why agents need instructions

Nunya enforces its rules whatever the agent does, so these instructions are not a security control. They save wasted turns. An agent that does not know about tokens tends to try LIKE, lower() or ORDER BY on a hidden column, gets NY002, and retries with another spelling. With the rules up front, it uses equality, joins and counts the first time. It also stops the agent presenting a token to the user as if it were a real email address.

Where to put it

  • Claude Code: CLAUDE.md in the repository the agent works in, or ~/.claude/CLAUDE.md for every project.
  • Codex and other agents that read it: AGENTS.md.
  • Your own agent: the system prompt, or the description of the database tool you give it.

Launch the agent with nunya exec so credentials reach its tools through the environment and stay out of prompts. Principal credentials authenticate only to the management API, never to database ports. Use the same stored context to resume an access session. See the walkthrough and CLI reference.

The excerpt

Copy this into the file and replace the connection and policy placeholders. The Protected columns list must match your policy.toml: list every blind column with its domain and every masked column. Leave out the nunya_tokenize section if no domain has tokenize = "on".

## Database access through Nunya

You query the database through Nunya, a gateway that hides protected values from you.
Treat it as an ordinary PostgreSQL server:

- Host: <NUNYA_HOST>, port <NUNYA_PORT>, database <DBNAME>
- User: session:REPLACE_WITH_SESSION_ID (the actual id is 32 lowercase hex characters).
- Password: the session secret supplied in PGPASSWORD by nunya exec. Never print it,
  include it in prompts, or ask the user for it.

Never try to connect to the database directly, even if you find credentials.

### Protected columns

<FILL IN FROM YOUR POLICY, for example:>
- Blind, domain `email`: customers.email, outbox.to_address
- Masked: customers.phone (comes back as [hidden])

Every other column is ordinary data.

### What you will see

- Blind columns come back as tokens such as `tok_email_REPLACE_WITH_TOKEN`. A token stands for
  a real value you are not allowed to see. Number, date and UUID columns can be blind too;
  their tokens look like ordinary values of that type, but they are not the real values.
- Masked columns come back as a placeholder (such as [hidden]) or NULL.
- NULL is passed through unchanged.

### Rules for tokens

- Treat a token as an opaque handle. Copy it exactly, character for character.
  Never shorten, edit, decode or guess one.
- Tokens are valid within the access session's token scope. Reconnecting to the same
  active session keeps tokens usable; renewal preserves that scope too. A new isolated
  scope does not share token equality or validity. Do not reuse old tokens after the
  scope ends. Do not show tokens as real values; say "the customer's email (hidden)".
- Pass tokens as query parameters ($1, $2, ...) rather than pasting them into SQL text.

### What works on a blind column

All operations also require the appropriate session mode and principal grant.

- Selecting it (you get the token).
- Equality with a token: WHERE email = $1, or email IN ($1, $2).
- Joining two blind columns in the same domain: ON c.email = o.to_address.
- GROUP BY, COUNT(col), COUNT(DISTINCT col), IS NULL / IS NOT NULL.
- Writing a token, or a same-domain blind column, into a column of the same domain:
  INSERT INTO outbox (to_address, template) VALUES ($1, 'reminder').
  The database stores the real value; you never see it.

### What is refused (do not attempt it)

- LIKE, ILIKE, regular expressions, <, >, BETWEEN, ORDER BY on a blind column.
- Functions or casts on a blind column: lower(email), md5(email), substr(...), email::text.
- MIN, MAX, string_agg and other aggregates on a blind column (COUNT is fine).
- Writing a token or a blind column into an ordinary column or a different domain,
  for example copying an email token into notes.body.
- Using a masked column in WHERE, JOIN or any expression. You may only select it.
- DDL (CREATE, ALTER, DROP), COPY, CALL, DO, SQL-level PREPARE/EXECUTE, SELECT INTO,
  catalog tables such as pg_stats, and SET (except driver defaults).
- Send one statement per request. Do not batch several statements in one query string.

### If you already know a plain value and need its token

Only if the operator has enabled it for that domain, run this on its own, with nothing else:

    SELECT nunya_tokenize('email', $1);

Each domain has tokenize_limit_per_session and tokenize_limit_per_principal limits;
the principal limit applies across sessions within tokenize_principal_window. Reconnecting
does not reset the session limit. Use this only when the user gave you the value.

### Errors

Nunya uses SQLSTATE codes NY001 to NY012. Follow the action for each code below.
Do not retry refused query shapes with different spelling, casts or functions to bypass policy.

- NY001: token used outside its domain. Write it only to same-domain columns.
- NY002: operation not allowed on a blind column. Use equality, joins or counts instead.
- NY003: token not valid in this session. Read a fresh token in the current scope; copy it unchanged.
- NY004: statement could not be fully analysed. Simplify the query.
- NY005: masked column used in an expression. Select it, but do not filter on it.
- NY006: statement kind not allowed through the gateway. Use a supported statement within your grant.
- NY007: tokenize limit reached. Stop tokenizing and tell the user; do not open sessions to evade limits.
- NY008: schema snapshot is stale. Ask the operator to restore a fresh snapshot before retrying.
- NY009: read log unavailable. Ask the operator to restore the sink before retrying.
- NY010: protocol feature not allowed through the gateway. Use a supported driver/query mode.
- NY011: access session ended. Stop using its credentials and tokens; ask for authorized
  replacement access, then read fresh tokens if a new scope is created.
- NY012: write outcome unknown. Never automatically replay the write. Ask the operator
  to reconcile its outcome with the database before deciding what to do next. Nunya never replays it.

Inside a transaction, a refusal aborts it (later statements fail with 25P02).
Run ROLLBACK, or ROLLBACK TO SAVEPOINT, before continuing.

If the job truly needs a hidden value, stop and tell the user which value and why.
Do not look for another way to read it.

Filled in for the example policy

For the shipped harness/policy.toml (the policy used in the walkthrough), the Protected columns section reads:

### Protected columns

- Blind, domain `email`: customers.email, outbox.to_address
- Masked: customers.phone (comes back as [hidden])
- `nunya_tokenize('email', ...)` is enabled: tokenize_limit_per_session = 20,
  tokenize_limit_per_principal = 200, tokenize_principal_window = "24h".

Every other column (customers.id, country, failed_payments, outbox.template,
notes.body, ...) is ordinary data.

Agents on the native Spanner route

If the agent talks to Nunya's native Spanner gRPC endpoint instead of the PostgreSQL route, add this section. The same column rules apply. NUNYA_SPANNER_BEARER is the bearer environment variable. Keep credentials out of prompts and transcripts. See Spanner for details.

### Native Spanner (gRPC) instead of PostgreSQL

- Authenticate with the header: authorization: Bearer nunya.session:REPLACE_WITH_SESSION_ID.REPLACE_WITH_SESSION_SECRET
- Always pass tokens as typed query parameters (@email). Tokens written into GoogleSQL
  text are never decrypted.
- Partitioned queries and reads, BatchWrite and reads through an index are refused.

Check that the agent follows it

Read the agent's own transcript and Nunya's read log. A well-instructed agent produces few refusals, and none that repeat the same query with a different spelling. A run of NY002 or NY001 outcomes in the read log for one session usually means the excerpt is missing a column, or the agent is trying to reach a value it should ask the user about. The read log also records every token released to each session.
