Keep the values behind the boundary

Nunya protects against an agent, or instructions injected into its context, reading protected values or moving decoded contents into an unapproved destination.

The threat model

Assume the agent can issue hostile SQL and reuse tokens it has received. A prompt injection may ask it to print contact details, probe them with patterns or copy them into another column. Nunya inspects SQL independently of the agent's stated intent. The gateway checks approved SQL against a policy and schema snapshot before forwarding it.

The agent must connect only to Nunya. Network isolation must prevent direct upstream connections, and upstream credentials must remain outside the agent environment. Mark every sensitive column: unmarked data is plain. The policy is an operator-controlled security boundary.

What the gateway protects

Blind results become tokens before reaching the agent. Approved same-domain writes and equality inputs decode inside the gateway. Masked outputs become placeholders or SQL NULL. Unsupported analysis and unsafe protected-column operations fail closed.

The demo's notes write receives NY001, token used outside its domain. Its LIKE probe receives NY002, operation not allowed on a blind column. Review token-detection limitations: unspecified binary PostgreSQL parameter types and Spanner ARRAY/STRUCT values have detection gaps. Do not treat the demo as a universal exfiltration guarantee.

What remains outside the boundary

A compromised Nunya host, stolen upstream credentials or direct database access can defeat this model. Protect configuration, upstream passwords, root keys, session state, TLS keys and logs. Plaintext transport belongs only on a trusted local network.

Nunya does not hide equality relationships within a domain and scope, or counts of shared values. It does not promise to cover every side channel. Do not infer protection against timing, row-count or broader inference attacks. Schema information, selected plain values and permitted aggregates remain visible.

The authenticated management listener requires TLS off loopback. Only administrators manage principals, credentials and grants or inspect other sessions and connections. The Unix mode-0600 socket at state_dir/nunya.sock carries administrator authority; Windows uses [[management.admin]] entries instead. Protect service-user access and configured administrator credentials. The separate admin listener has unauthenticated health, metrics and reload routes: keep it private. Read logs may contain query text and tokens and require their own access controls.

Root keys and scope derivation

The root key is 32 bytes. A key file can contain raw bytes or hexadecimal text; the environment form uses 64 hexadecimal characters. HKDF-SHA256 derives a scope secret from the root key and random scope salt, then separates subkeys by domain and purpose. Text tokens use AES-SIV with domain-associated data.

Root and scope key types erase owned secret material on drop and redact Debug output. These measures do not protect a compromised host. Restrict key and state access. The durable store checks the root key at startup and refuses a different key. Replacing it is an explicit continuity break; existing tokens no longer decode. See recovery.

Numeric/date format-preserving tokens and UUID permutations have no authentication tag. An arbitrary in-range typed value can decode under the current scope; wrong-scope typed tokens do not necessarily cause NY003. Text AES-SIV tokens authenticate their scope and domain.

Authentication and lifetime

Database ports accept only access-session credentials. PostgreSQL uses SCRAM-SHA-256 with user session:<32 hex> and the session secret. Native Spanner uses Authorization: Bearer nunya.session:<32 hex>.<secret>. Principal credentials authenticate only to the management API, as nunya.<principal>.<secret> bearer credentials. Sending a principal credential to a database port fails uniformly with NY003, like an unknown user.

Helpers generate secrets client-side. The service stores SCRAM verifiers and hashes, never the original secrets. The helper's private sessions.json does contain session credentials: protect its directory, output from session env, and child environments. Use TLS outside trusted local development and keep credentials out of source control and shared shell histories.

Each access session owns a token scope. Reconnects and renewals preserve it; separate sessions keep their scopes separate. Use --isolated for independent workflows under one principal. Labels are audit data only. The helper requires explicit --new-scope consent to replace an ended stored session; obtain fresh tokens after replacement. Typed format-preserving tokens lack scope authentication, as described above, so correct scope handling remains essential.

Defaults are 8 hours absolute and 1 hour idle. Renewal revalidates the principal and grants within the absolute limit. Revocation, expiry and principal disablement terminate active work; NY011 reports an ended session and NY012 reports an unknown write outcome. Do not replay a write without reconciling it. See lifetimes, CLI reference and errors.

Evidence and its limits

A non-interference property test runs 500 random queries per seed over four seeds: 2,000 queries total. It checks that changing hidden values never changes what the agent sees. This is bounded evidence for the tested property, not proof for every statement or deployment.

Nunya's test suite runs the worked example against PostgreSQL 16, 17 and 18. psycopg 3 and pgJDBC 42.7.3 are tested end to end in a seven-step driver check.

Uncertainty is an explicit refusal

Unanalysable statements, stale schema snapshots and unavailable read logs are refused. If lifecycle audit is unavailable, session issuance is undone by revocation, while renewal leaves the session unchanged; both return 503 audit_unavailable. Revocation and disablement still take effect but also return 503. Authentication failures are uniform and do not disclose whether an identity exists. Invalid PostgreSQL policy reloads retain the previous policy. Use the error reference to diagnose failures without weakening the boundary. Agent-facing refusal messages are fixed; static internal hints are not included in their Display output.
