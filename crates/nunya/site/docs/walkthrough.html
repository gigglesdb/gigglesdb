From principal to access session

Read a protected value, reconnect with its token, then end access. This flow uses the seeded PostgreSQL app database and harness policy from the quickstart. Results are described rather than presented as a captured run.

On this page1. Start the gateway2. Authorize the agent3. Acquire access4. Read and reconnect5. Renew6. RevokeInspect the read log

1. Operator: start the gateway

Prepare the private configuration, upstream credentials, root key, policy and management administrator described in the quickstart. Run from that private directory:

nunya policy check --config nunya.toml
nunya serve --config nunya.toml

Keep this process running. It owns the upstream connection and enforces policy. The agent connects to Nunya on PostgreSQL port 6432; management uses port 6481 in this local example. Use verified TLS for remote traffic. For later changes, consult reload and restart rules.

2. Operator: create a principal and grant

In a trusted second terminal, authenticate as the configured management administrator. Replace the administrator secret-file placeholder with a private file containing its password on the first line.

nunya principal create reporting-agent --kind agent --server http://127.0.0.1:6481 --principal operator --principal-secret-file REPLACE_WITH_ADMIN_SECRET_FILE
nunya principal grant reporting-agent --route postgres=read-only --server http://127.0.0.1:6481 --principal operator --principal-secret-file REPLACE_WITH_ADMIN_SECRET_FILE
nunya principal credential add reporting-agent --generate-secret --server http://127.0.0.1:6481 --principal operator --principal-secret-file REPLACE_WITH_ADMIN_SECRET_FILE

The credential command prints a credential identifier and a one-time secret. Save only the secret line in a private file, referenced below as REPLACE_WITH_PRINCIPAL_SECRET_FILE. The grant allows reads on route postgres. This principal authenticates only to management to request access; it cannot log in on the database port. Do not pass administrator or upstream credentials to the agent.

3. Agent side: acquire a session

Use the agent principal to acquire or resume a stored session:

nunya session acquire --server http://127.0.0.1:6481 --principal reporting-agent --principal-secret-file REPLACE_WITH_PRINCIPAL_SECRET_FILE --context reporting --route postgres --ttl 1h
nunya exec --server http://127.0.0.1:6481 --principal reporting-agent --principal-secret-file REPLACE_WITH_PRINCIPAL_SECRET_FILE --context reporting -- psql -d app

The helper saves credentials in private sessions.json under its per-user state directory (overridable with NUNYA_HOME). Acquire prints public details, not the session secret. exec supplies PGHOST, PGPORT, PGUSER and PGPASSWORD to the child. The login is session:REPLACE_WITH_SESSION_ID (an actual ID has 32 lowercase hex characters); its password is the session secret. Prefer launching the agent itself with nunya exec to keep credentials out of prompts.

The session binds access to a principal, route, mode, expiry and token scope. A TCP connection is only one use of that session. Keeping the same context lets the helper resume it after a disconnect. Run the next SQL in psql, then exit with \q:

SELECT id, email, phone FROM customers WHERE failed_payments >= 2 ORDER BY id;

Email values are opaque tokens; phones are masked placeholders. The agent learns which customers need attention without learning their contact details.

4. Read a token, reconnect and reuse it

Save the following as session_demo.py in your private example directory. It requires Python with Psycopg 3 installed. Both connections inherit the same access session from exec. The token stays in memory and is passed as a bound parameter, never pasted into SQL.

import psycopg

with psycopg.connect(dbname="app") as conn:
    row = conn.execute(
        "SELECT email FROM customers WHERE id = %s", (3,)
    ).fetchone()
    if row is None:
        raise SystemExit("Seed customer missing")
    token = row[0]

# The first connection has closed; the access session remains active.
with psycopg.connect(dbname="app") as conn:
    rows = conn.execute(
        "SELECT id, country FROM customers WHERE email = %s", (token,)
    ).fetchall()
    print(rows)
nunya exec --server http://127.0.0.1:6481 --principal reporting-agent --principal-secret-file REPLACE_WITH_PRINCIPAL_SECRET_FILE --context reporting -- python session_demo.py

The second query finds the same customer using equality on the blind email column. Closing a connection does not erase the session scope, so the first token remains usable. A new isolated scope has different token equality and does not accept these tokens. session acquire --isolated creates a separate scope in a new context; use a fresh context name. Supported connection metadata probes are documented in drivers.

Approved writes and domain boundaries

This example grants read-only access. With an operator-approved read-write grant and session mode, a bound email token can be written to outbox.to_address because both columns use domain email. The database stores the underlying address. Copying it to ordinary notes.body is refused with NY001. Never broaden access merely to work around a refusal.

Reading a value again

Within the same active token scope, reading the same blind value in the same domain returns the same token, including across reconnects. Tokens are handles for approved operations, not anonymized values to export or interpret.

Use equality, not probing

The parameterized lookup above is allowed. LIKE, ordering or functions on a blind email column are refused with NY002; using a masked phone in an expression is refused with NY005. Use the plain columns for ordinary analytics.

5. Renew while the session is active

nunya session renew --server http://127.0.0.1:6481 --principal reporting-agent --principal-secret-file REPLACE_WITH_PRINCIPAL_SECRET_FILE --context reporting
nunya session show --server http://127.0.0.1:6481 --principal reporting-agent --principal-secret-file REPLACE_WITH_PRINCIPAL_SECRET_FILE --context reporting

Renewal revalidates access and refreshes last-used time while preserving the session and token scope. It does not extend the absolute expiry. This example requested one hour; the configured maximum defaults to eight hours, with a one-hour idle timeout. renew --rotate rotates the stored credential while preserving scope. Renewal cannot revive an expired or revoked session.

6. Revoke and observe NY011

First leave an interactive connection open in one terminal:

nunya exec --server http://127.0.0.1:6481 --principal reporting-agent --principal-secret-file REPLACE_WITH_PRINCIPAL_SECRET_FILE --context reporting -- psql -d app

In psql, run \set VERBOSITY verbose so errors show SQLSTATE codes. In another terminal, end that session using the same helper state and context:

nunya session revoke --server http://127.0.0.1:6481 --principal reporting-agent --principal-secret-file REPLACE_WITH_PRINCIPAL_SECRET_FILE --context reporting

Revocation ends the session and removes its stored context. In the already-open psql connection, submit:

SELECT id FROM customers;

The gateway refuses further work with NY011, access session ended, and closes the connection. Do not reuse its credentials or tokens. Expiry also ends access. If a write was forwarded but its result could not be observed, NY012, write outcome unknown, means an operator must reconcile it; Nunya never replays it.

If acquire or exec finds an ended session still stored locally, it requires explicit --new-scope permission before replacing it. Revocation above removed the local context, so a later acquire creates a new session; do not assume token continuity. Obtain fresh tokens whenever the scope changes.

Inspect the read log

The policy read-log sink records released tokens and refusals. Inspect it from the operator side to understand what the agent was allowed to see. Keep it private: a token is still an access handle. See agent instructions for actions on every NY code.
