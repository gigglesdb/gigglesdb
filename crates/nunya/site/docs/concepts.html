The vocabulary of a protected query

Principals receive grants, access sessions carry token scopes, and policy domains define where protected values may move.

Blind, masked and plain columns

TreatmentAgent receivesPurpose
BlindA typed, scoped tokenCarry a value into an approved position
MaskedA placeholder or SQL NULLHide an output without a reusable handle
PlainThe original valueOrdinary identifiers and analytics

Each policy column chooses a declared blind domain or masked = true. Unmarked columns are plain. Masking is an output treatment, not permission to filter or compute on a hidden value. A placeholder requires a textual column.

Domains define permitted transfers

A domain groups compatible protected columns. In the example, customers.email and outbox.to_address share the email domain. An email token can queue a reminder without exposing the address. Sharing a domain authorizes transfers: review every column added to it.

[domains.email]
tokenize = "on"
tokenize_limit_per_session = 20
tokenize_limit_per_principal = 200
tokenize_principal_window = "24h"

[[column]]
table = "public.customers"
name = "email"
blind = "email"

[[column]]
table = "public.outbox"
name = "to_address"
blind = "email"

Domain names start with a lowercase letter and contain lowercase letters, digits or underscores, up to 31 characters. Participating columns need compatible types and ranges. See policy reference.

Principals and grants

A principal is a person, agent or service identity. It is API-managed or config-managed, enabled or disabled, and may have administrator authority. Principal credentials authenticate only to management. An enabled principal can acquire, inspect, renew and revoke its own sessions within its grants; administrators also manage identities, credentials and grants and inspect other sessions and active connections.

A grant names a route and maximum mode: read-only or read-write. No grant means no session on that route. Read-only sessions refuse write statement kinds with NY006; native Spanner also refuses DML, Commit mutations and BatchWrite. Reducing a grant applies on the next execution; widening it requires renewal or a new session. Grant replacement replaces all existing grants. See principal commands.

Access sessions and continuity

An access session has a principal, route, mode, credential, expiry and its own token scope. PostgreSQL accepts only session:<32 hex> with the session secret through SCRAM-SHA-256. Native Spanner accepts Authorization: Bearer nunya.session:<32 hex>.<secret>. Principal credentials cannot be used on either database port.

The helper generates secrets client-side; the service stores verifiers and hashes only. Reconnects and renewals preserve scope, so tokens retain their meaning within that session. Tokens from a different session must not be reused. An ended stored session is not silently replaced: the helper reports the scope replacement and requires --new-scope before continuing with a new scope and fresh tokens.

Routes

A route identifies a database destination. The PostgreSQL-wire [upstream] defaults to route postgres; [spanner_native] defaults to spanner-native. Each supports a route_id override. Grants and sessions refer to these IDs. Changing the database behind an existing route ID breaks continuity; treat it as an explicit migration. See configuration.

Token scopes and equality

Repeated values in one domain and scope produce stable tokens. Equality and grouping remain useful, but equality relationships and counts remain visible. NULL passes through unchanged. A token is a handle for its approved scope and domain, not a public identifier.

Text tokens use deterministic AES-SIV and have the form tok_<domain>_<base32>. Text is padded into buckets before encryption, with input limited to 254 bytes. Numbers and supported date/time types use format-preserving conversion; UUIDs use a permutation. Supported types include text, varchar, bpchar, int4, int8, date, timestamp, timestamptz and UUID. Declared ranges must fit every participating type and contain at least 2^20 values.

Numeric/date tokens and UUID permutations have no authentication tag or self-identifying text prefix. An arbitrary in-range value can decode under the current scope, so foreign-scope typed tokens are not reliably rejected as NY003. Always preserve the correct scope. Text tokens authenticate their domain and scope.

Workflow isolation

Use nunya session acquire --isolated for a workflow that must not share tokens with another workflow, such as independent agent runs under one principal. It creates a separate scope and, without an explicit context, an automatically named context. An explicit context must be unused. Reuse the resulting context to reconnect.

--label is audit data only: it never selects, merges or grants access. exec does not accept --isolated; acquire the isolated context first, then use exec with that context. See CLI reference.

Token lifetimes

Tokens are usable through their access session. Defaults are an 8-hour absolute lifetime and a 1-hour idle timeout. Renewal revalidates the principal and grants and extends idle time within the absolute limit; it does not reset that limit or change the scope.

To shorten lifetimes, lower [session] max_lifetime and idle_timeout, or request a shorter session with --ttl 1h. A requested TTL cannot exceed the configured maximum. Durations are positive decimal integers with a lowercase s, m, h or d suffix. Configuration maximum lifetime is 1 minute through 30 days; idle timeout is at least 1 minute and no greater than the maximum. idle_timeout = "off" disables idle expiry.

[session]
max_lifetime = "2h"
idle_timeout = "15m"

See lifetime settings and acquisition and renewal.

Tokenization limits

SELECT nunya_tokenize('email', 'carol@example.test'); explicitly tokenizes known plaintext for an approved lookup. It is opt-in per domain and defaults to off. Repeated guesses can become an oracle; enable it only for a justified workflow. The plaintext argument is redacted from the read log.

Enabling it requires tokenize_limit_per_session, tokenize_limit_per_principal and tokenize_principal_window. The principal limit must be at least the session limit. The fixed-length principal window starts with the first tokenization after the previous window ends; restart, reconnect and a new session cannot reset it. Either exhausted limit refuses with NY007. Limit changes apply to the next tokenization without clearing counters. Ordinary protected SELECT output is separate. See policy limits.

The read log is part of the boundary

Read logs record time, principal, session, scope, connection, credential ID, route, policy and config revisions, statement fingerprint, redacted SQL, outcome, released-row count and tokens. Stdout and rotating-file sinks are supported; the file sink keeps one predecessor. Sink failures cause NY009 refusals. Ordinary forwarded PostgreSQL statements can produce both an initial rows=0 intent and a completion entry, so entries are not unique queries.

Lifecycle audit records cover session changes. If that sink is unavailable, issuance and renewal fail closed. Query text and tokens may be sensitive: restrict permissions and retention. See operations.
