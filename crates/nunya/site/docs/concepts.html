The vocabulary of a protected query

The policy describes which values an agent may carry, which values it may see, and which operations preserve that boundary.

Blind, masked and plain columns

TreatmentAgent receivesPurpose
BlindA typed, scoped tokenCarry a value into an approved position
MaskedA placeholder or SQL NULLHide an output without a reusable handle
PlainThe original valueOrdinary identifiers and analytics

Each policy column chooses exactly one treatment: a declared blind domain or masked = true. Unmarked columns are plain. Masking is an output treatment, not permission to filter or compute on a hidden value. A placeholder requires a textual column.

Domains define permitted transfers

A domain groups compatible protected columns. In the example, customers.email and outbox.to_address share the email domain. An email token can queue a reminder without becoming visible to the agent. Sharing a domain is a deliberate grant: review every column added to it.

[domains.email]
tokenize = "on"
tokenize_limit_per_task = 20

[[column]]
table = "public.customers"
name = "email"
blind = "email"

[[column]]
table = "public.outbox"
name = "to_address"
blind = "email"

Names start with a lowercase letter and contain lowercase letters, digits or underscores, up to 31 characters. Participating columns need compatible types and ranges. See Policy reference.

Tokens preserve type, scope and equality

Text tokens use deterministic AES-SIV encryption and have the form tok_<domain>_<base32>. Text is padded into buckets before encryption, with input limited to 254 bytes. Numbers and supported date/time types use format-preserving conversion; UUIDs use a block permutation. A typed token is not necessarily recognizable by a tok_ prefix.

NULL passes through unchanged. Supported token types include text, varchar, bpchar, int4, int8, date, timestamp, timestamptz and UUID. Range declarations must fit the participating types and contain at least 2^20 values. Small domains and unsupported types cannot simply become blind columns.

Repeated values in one domain and scope produce stable tokens. This enables equality and grouping, but exposes equality relationships and counts. A token is a handle within its permitted scope, not a public identifier to publish.

Format-preserving numeric/date tokens and UUID permutations have no authentication tag or self-identifying text prefix. An in-range value decodes under the current scope; wrong-scope typed values are not reliably detected as invalid. Use the correct scope to preserve meaning. Authenticated text tokens provide a different integrity contract.

Tokenize a known plain value

An agent may already know a value and need a token for an approved lookup. The explicit nunya_tokenize operation is opt-in per domain. Tokenization defaults to off. Enabling it requires a per-task limit between 1 and 100000; task counts are persisted, so reconnecting to the same task does not reset them. PostgreSQL standing-credential counts are session-local.

SELECT nunya_tokenize('email', 'carol@example.test');

This syntax example uses a value from the demo; it is not an additional recorded result. The plaintext argument is redacted from the read log. Repeated guesses can turn tokenization into an oracle; enable it only for a justified workflow.

Task scopes and expiry

Opening a task creates a random identifier, one-time secret, expiry and random scope salt. The stored record contains a secret hash and SCRAM verifier rather than the original secret. Listing tasks does not reveal their secrets. TTL units are seconds, minutes or hours.

Unknown, closed, expired and wrong-secret tasks share an authentication refusal. Closing a task removes its persisted record and salt. PostgreSQL validates task liveness at connection startup; an already authenticated session retains its scope keys. Closing or expiring a task does not generally terminate that existing PostgreSQL connection. Explicit tokenization checks the live task again. Native Spanner revalidates task authentication per RPC, including cached sessions.

Standing credentials

Standing credentials are configured identities backed by SCRAM verifiers. PostgreSQL standing sessions get a fresh random scope salt at connection time, so their tokens are not stable across reconnects. Use a task when the workflow needs a deliberately bounded authentication lifetime and task scope.

Task and standing secrets are credentials. Keep them away from unrelated agents and protect transport with TLS outside trusted local development. The scope keys and root key are gateway internals, not values the agent needs.

The read log is part of the boundary

Each JSON-line record contains a timestamp, task, credential, statement fingerprint, redacted statement text, outcome, released-row count and released tokens. stdout and rotating-file sinks are supported. The file sink keeps one rotated predecessor. Sink failures cause NY009 refusals.

Ordinary forwarded PostgreSQL statements can produce an initial rows=0 intent record and a completion record; this is not limited to extended-protocol prepared statements. The walkthrough uses the supplied abridged demo capture. Query text and tokens may be sensitive: restrict permissions and retention.
