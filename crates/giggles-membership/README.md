# giggles-membership

A reusable, bounded prerequisite for membership changes in one trusted-owner Raft group. It replaces one voter by adding a fresh learner, establishing durable catch-up, entering explicit joint consensus, and leaving joint consensus. It does not integrate with the current fixed-membership database runtime or move a range.

`Membership` is a deterministic controller. Persist it with the group's actual `ConfState`, application index and application state in one atomic storage transaction. `Command` carries group/owner epoch; `Intent` carries a stable ID, membership epoch, fresh learner ID and voter to remove. Repeating Begin with identical identity/payload finds the retained receipt; changing its payload rejects. `Change` derives exact `ConfChangeV2` bytes and context. Apply only the matching committed entry through `RawNode::apply_conf_change`, validate its returned configuration with `applied_configuration`, and atomically publish the controller and returned `ConfState` at that entry's applied index. Configuration proposals must be serialized behind the applied administrative barrier. Never reuse node IDs.

`durable::{Store, Node}` is a membership-only reference adapter using raft 0.7 and redb Immediate transactions. It persists Ready log/hard state before publishing responses, applies controller/ConfState/index atomically, then processes LightReady and advances application. Every `drive` error fences the actor; discard all its output, drop all Store clones and reopen the file. An ambiguous commit may already be durable. Reopening restores configuration and progress at the applied index, then replays any remaining committed entries. `Store::compact` snapshots only applied state and retains unapplied tail. Snapshots bind group, controller, ConfState, term and index. Storage mechanics use raft's MemStorage over the durable image. This driver intentionally has no SQL/data plane or transport.

The integrating owner must:

- Authenticate administrative callers and peer/group identities outside these APIs. Public structs and serde encodings are trusted engine inputs, never client authorization tokens. `Fence` is a committed owner-controlled monotonic authority change, not proof of external authority. A file owner can replace state.
- Provision the new process with the same group identity and initial committed voters; authenticate it as a permitted learner peer. Keep outgoing voters routable through joint consensus, and reject cross-group traffic. `Node::step` checks sender/recipient, size and prohibited local/client message types; it relies on the caller's authenticated roster. Delayed responses from peers absent from raft progress are dropped.
- Install a snapshot and replay tail through the learner's durable application path. Obtain an authenticated durable applied acknowledgment bound to group, learner, intent, membership epoch and current leader term. Supply `Readiness` with an applied barrier at least the learner-add entry. The reference adapter also checks local durable apply and leader match progress. A match index alone never proves application durability; this assertion must come from the trusted adapter, not an untrusted client.
- Refresh readiness after a term or owner-epoch change before proposing promotion. Recovery may commit an already proposed old-term configuration; its durable barrier remains valid. Do not reinterpret a previously committed intent as a new command.
- Continue explicit LeaveJoint after restart/election. A new leader can resume from `Membership::progress`; there is no hidden automatic reconciler. The reference adapter steps a removed leader down after durable apply because raft 0.7 leaves that step as an upstream TODO.
- Include all real database state in the same snapshot and atomic application batch. GD19 currently derives a fixed ConfState, rejects configuration entries and limits transport membership; its owner must replace those assumptions together. Do not point the database at the reference membership-only snapshot format.
- Handle admission limits explicitly. Voters: 1–31; receipts: caller limit 1–1024; one active replacement; one pending administrative proposal; entries: 4 KiB; retained log: 4096 entries; snapshots: 2 MiB. Compact before the log fills. Receipts are never silently evicted, and capacity exhaustion rejects new intents while allowing recovery/completion of the active intent. Increasing limits or introducing receipt GC requires a separately defined replay horizon.

Run the executable replacement example with a new artifact directory (files are retained):

```text
cargo run --manifest-path crates/giggles-membership/Cargo.toml --example replace -- PATH
cargo run --manifest-path crates/giggles-membership/Cargo.toml --bin membership-recover -- PATH/node-1.redb
```

The example runs actual RawNodes and durable files under a deterministic in-process message scheduler. The `membership-recover` executable also exposes trusted `before`/`after` subprocess exit seams. Tests distinguish modeled atomic failures, actual process exits and in-process partitions; none demonstrate power-loss/device failure, network authentication, online range movement, provider survival or production readiness. Tests retain unique raw redb artifacts under ignored `artifacts/` and never remove files.

Verification: `cargo fmt --check`, `cargo clippy --all-targets -j 2 -- -D warnings`, `cargo test -j 2`, `cargo test --release -j 2`, `cargo test --doc -j 2`, and `RUSTDOCFLAGS="-D warnings" cargo doc --no-deps -j 2`, each with this crate's manifest. Independent primary review and database owner adapter integration remain required.
