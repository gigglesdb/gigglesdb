# GigglesDB distributed transactions release notes

These notes describe how transactions behave when a database runs as a
cluster of range groups, where every node accepts SQL, as of 2026-11-17.
Design, plan and evidence: GD-0075 (spec, plan and work log).

## 1. Isolation levels

All three PostgreSQL isolation levels run on one node and on every node of a
cluster, and `SHOW transaction_isolation` reports the level that actually runs.

| Requested level | Runs as |
|---|---|
| `READ UNCOMMITTED`, `READ COMMITTED` (default) | READ COMMITTED |
| `REPEATABLE READ` | snapshot isolation at the transaction's first statement |
| `SERIALIZABLE` | snapshot reads, then the read set is locked and revalidated at `COMMIT` |

How SERIALIZABLE works:

- Reads take no locks. A SERIALIZABLE transaction reads at its snapshot, like
  REPEATABLE READ, and records what it read: the keys of point reads and the
  key intervals it scanned.
- At `COMMIT`, a transaction that wrote anything takes shared locks on the
  keys it read and shared gap locks on the intervals it scanned, range by
  range in key order. Each key lock comes back with the key's newest
  committed version; each scanned interval is read again at a fresh
  timestamp once its locks are held. If anything it read has a newer
  committed version than its snapshot, the transaction fails with `40001`
  (serialization_failure). Otherwise it commits. Its locks are held until the
  commit is decided: they are written into each range's prepared record, so
  they survive a leader change after the commit has prepared. A leader change
  that loses them before that makes the commit fail with `40001`.
- A read-only SERIALIZABLE transaction commits at its snapshot in a cluster.
  On a single node it is validated like a writer (see 2.1).
- Committed writers are therefore serialized in commit-timestamp order.

## 2. Differences from PostgreSQL

Each behavioural difference below was checked against PostgreSQL 18.6 and
is pinned by a test that runs the same steps on both. In every case the database stays serializable (or, at
REPEATABLE READ, snapshot-consistent): no anomaly PostgreSQL prevents is let
through. The differences are in which transaction fails, when it fails, which
SQLSTATE it gets, and whether it waits.

### 2.1 SERIALIZABLE

1. **A COMMIT can wait for writers of what it read.** A SERIALIZABLE
   `COMMIT` waits while another open transaction holds an exclusive lock on a
   row, or a key in an interval, that the committing transaction read.
   PostgreSQL does not wait. In a write-skew pair, the first `COMMIT` waits
   and finishes after the second transaction fails with `40001`. (Cluster.)
2. **A writer whose read changed fails.** A transaction that writes, and read
   a row that another transaction has since changed and committed, fails with
   `40001`, even when no dependency cycle forms. PostgreSQL commits it when
   no cycle exists. (Single node and cluster.)
3. **A different transaction may be chosen to fail.** When both transactions
   of a conflicting pair reach `COMMIT`, the younger one is aborted with
   `40001`. PostgreSQL may fail the other one, or fail an earlier statement.
   For example, with a parent `DELETE` racing a child `INSERT`, PostgreSQL
   fails the `DELETE` with `23503` and commits the `INSERT`, while GigglesDB
   may abort the younger transaction with `40001`. The final state is
   serializable and never has an orphan row. (Cluster.)
4. **Failures move to COMMIT.** In the read-only anomaly (Fekete et al.),
   PostgreSQL fails the writer's `UPDATE` with `40001`; GigglesDB fails its
   `COMMIT` (single node and cluster). In a cluster, when a child `INSERT`
   follows a parent `DELETE` committed after the child's snapshot, the child
   fails with `40001` at `COMMIT` rather than at its `INSERT`. The final state
   is the same.
5. **Read-only transactions on a single node.** On a single node, a read-only
   SERIALIZABLE transaction whose reads were overwritten after its snapshot
   fails `COMMIT` with `40001`. PostgreSQL commits it. In a cluster it commits.
6. **Validation has a budget.** Revalidating the read set at `COMMIT` reads at
   most one million row versions (one per point read, one per version
   scanned in an interval). A transaction whose read set needs more fails
   with `40001` instead of committing. (Single node and cluster.)
7. **SERIALIZABLE cursors are buffered.** A cursor opened in a SERIALIZABLE
   transaction holds its rows in memory, bounded by the cursor buffer limit,
   as cursors in a writing transaction already were.

### 2.2 REPEATABLE READ (and SERIALIZABLE where noted)

1. **Duplicate insert.** Inserting a key that a concurrent transaction
   committed after this transaction's snapshot fails with `40001`.
   PostgreSQL fails it with `23505` (unique_violation).
2. **Child of a newer parent.** In a cluster, inserting a child row whose
   parent was inserted and committed after the transaction's snapshot fails
   with `40001`. PostgreSQL fails it with `23503` (foreign_key_violation).
3. **Deferred foreign keys.** At REPEATABLE READ and SERIALIZABLE, a
   `DEFERRABLE INITIALLY DEFERRED` foreign key whose parent changed since the
   snapshot fails with `40001` at the `INSERT`.
   PostgreSQL fails at `COMMIT`.

## 3. Large results in a cluster

- **SELECT results stream.** A `SELECT` on any node reads the ranges page by
  page as the client fetches, as on a single node, so a large result needs no
  memory for the whole result. Statements in a transaction that has already
  written rows, SERIALIZABLE transactions, statements that use sequences, and
  statements the streaming planner cannot run still produce their whole
  result first, within the cursor buffer limit (256 MiB per statement).

## 5. The legacy range runtime is retired

The first multi-range prototype, the `giggles-ranges` binary in
`crates/giggles-distributed`, ran ranges as whole-database images with their
own Raft groups and served transactions through trusted owner controls. It was
removed once ranges, gateways and cross-range commit were in place (GD-0075
plan items R5-120 and R5-121), together with the crates that existed only to
drive it:

- `crates/giggles-distributed`, with the `giggles-ranges` binary;
- `crates/giggles-placement`, its failure-domain placement controller;
- `crates/giggles-range-history`, its history campaign runner;
- `crates/giggles-membership`, its reference membership controller;
- the `distributed` and `range-history` tasks of `scripts/dev.sh` and
  `dev.ps1`, and their IDE run configurations.

`giggles-history` (the history checker), `giggles-topology` and
`giggles-transactions` stay.

## 6. Splitting ranges as they grow

A cluster splits a range when its stored size reaches a threshold. Set the
threshold in the `cluster` section of every node's configuration:

| Field | Meaning |
|---|---|
| `split_size_bytes` | Turns on live splits. A range this node leads splits once its approximate stored size reaches this many bytes. At least 65536. |
| `split_interval_ms` | How often each node checks the ranges it leads. Default 1000; 100 to 3600000. Needs `split_size_bytes`. |
| `split_cooldown_ms` | Minimum time between two size splits of one range on a node. Default 10000; at most 86400000. Needs `split_size_bytes`. |

Splits happen while the database is in use:
- A statement that meets a split retries inside the server, or fails with `40001`.
- Splits are permanent: ranges are not merged again.
- Upgrade every node before the first split or range move. Both write formats that older builds cannot read.

Procedures are in the GD-0075 runbooks "Split ranges as they grow", "Move a range replica" and "Replace a lost node and handle node failures".

## 7. Known limitations

- **Each statement makes several round trips between nodes.** A node checks the session's role and authority for every statement, reading them from the system range at a fresh timestamp, and then calls the range leaders. Statement latency therefore grows with the distance between nodes:
  - with 12 to 24 ms between nodes, a single-row INSERT took about 2 s;
  - across sites 1 to 44 ms apart, an UPDATE took 128 to 344 ms against 6 ms in a single replicated group.

  Run a cluster's nodes in one data centre. Load data with multi-row INSERTs or COPY rather than one statement per row.
- **Pipelined replies wait for Sync.** A client that pipelines many statements, as `executemany` does, sees no replies until the pipeline's Sync, even while the statements are running.
- **Contention on one row can cause false deadlocks.** When many transactions update the same row through several nodes, deadlock detection can report a cycle that does not exist, and abort transactions with `40P01` instead of making them wait. No update is lost. Retry the transaction. In a write-skew pair this can also abort the older transaction rather than the younger one.
- **Range sizes count flushed data only.** The size used by the split policy and shown by `cluster status` counts only data RocksDB has written to disk files, after compression. Data still in memory counts as 0; that is up to 64 MiB per keyspace, shared by all its ranges. So a small, recently written range splits only after its keyspace flushes.
- **The system range must keep a majority.** While two of the three replica nodes of the system range (range 1) are down:
  - no range can elect a leader;
  - about 6 s later every node refuses statements with `40001`, until the system range has a majority again.

  Place the system range's replicas in independent failure domains.
- **A node cannot rejoin a range it moved off.** Move the replica to a different node instead. The node it left keeps that range's data on disk until it restarts.
- **Conflict errors under contention.** When several nodes insert the same value into a unique column at once:
  - at READ COMMITTED, `INSERT ... ON CONFLICT DO NOTHING` can fail one waiting transaction with `40P01` where PostgreSQL skips the row (also on a single node);
  - in a cluster, some of the losing inserts can fail with `XX000` instead of `40001`.

  Uniqueness always holds. Retry the transaction.
- `INSERT ... SELECT ... FROM generate_series(...)` is refused by a cluster node with `0A000`.
- A single node holds at most 128 tables, and a statement's text is at most 64 KiB (`54000` beyond either). Send large values as bound parameters.
