# GigglesDB replication release notes

## 1. What this release is

A v2 database can now be kept as three full, durable copies on three
machines (three Raft voters). A commit is acknowledged only after a majority
has it durably, so losing any one machine loses no acknowledged commit, and a
new leader takes over without operator action. Replication is a mode of
`giggles-server`; a database created without it behaves exactly as before.

These notes cover main through `0a2143fd` (2026-11-16). Design and evidence:
GD-0074 (spec, plan and work log).

## 2. Running a three-node cluster

Add a `replication` section to each node's server config. `database` is the
replicated data directory.

```json
"replication": {
  "node_id": 1,
  "cluster": "0123456789abcdef0123456789abcdef",
  "listen": "10.0.0.1:7001",
  "log_dir": "/var/lib/giggles/raftlog",
  "peers": [
    {"id": 2, "address": "10.0.0.2:7001", "fingerprint": "<64 hex>"},
    {"id": 3, "address": "10.0.0.3:7001", "fingerprint": "<64 hex>"}
  ],
  "operators": [{"name": "on-call", "fingerprint": "<64 lowercase hex>"}],
  "owner": "owner"
}
```

- `cluster` is the shared 16-byte database identity (32 lowercase hex). Every
  node of one cluster uses the same value.
- `peers` lists exactly the two other voters. Peers authenticate with mutual
  TLS. Each node needs its own leaf certificate (SAN `localhost`, server and
  client auth) from the cluster CA.
- `fingerprint` is the lowercase hex SHA-256 of the peer's leaf certificate
  (DER). The peer TLS identity defaults to the server's `certificate`,
  `private_key` and `client_ca`.
- `operators` optionally lists named operator certificate fingerprints (64 lowercase
  hex). They must be unique and separate from all node certificates.
- `log_dir` holds the Raft log. `snapshot_dir` defaults to
  `<log_dir>.snapshots`. The data, log and snapshot directories must be
  three separate siblings.
- Optional: `tick_ms` (default 100), and `write_set_bytes`, the largest
  transaction (at most 32 MiB).
- Validation errors name the field, for example `replication.peers[1].id`.

Each process prints its addresses with `role=leader term=<t> node=<id>` or
`role=follower node=<id>` on stdout.

## 3. Connecting clients

Only the leader runs SQL. Followers refuse PostgreSQL sessions right after
startup with `FATAL 57P03` (cannot_connect_now). Their native, HTTP and gRPC
ports are not bound. List all three hosts and ask for a read-write server:

```text
postgresql://owner@10.0.0.1:5432,10.0.0.2:5432,10.0.0.3:5432/postgres?target_session_attrs=read-write
```

libpq and pgJDBC move on to the next host on 57P03.

When a leader loses leadership, its sessions end with `FATAL 57P01`
(terminating connection). Reconnect with the same multi-host string.

Every statement on the leader first confirms leadership with a majority (a
read barrier). An isolated old leader can neither commit nor answer a read.

## 4. Lost replies

If a client loses the reply to `COMMIT` (for example the leader dies), it
can find out what happened:

```sql
BEGIN;
-- ... writes ...
SELECT pg_current_xact_id();   -- remember x before COMMIT
COMMIT;                        -- reply lost
-- after reconnecting, on any later leader:
SELECT pg_xact_status(x);      -- 'committed' or 'aborted'
```

Differences from PostgreSQL:
- `pg_current_xact_id()` returns `bigint`; there is no `xid8` type.
- `pg_xact_status()` accepts an integer.
- Transaction ids are assigned on demand, and they are durable across restarts
  and leader changes.

Native `once` operations (embedded and native API) work on replicated
databases. The receipt is stored in the same replicated write as the rows it
protects. After a leader change, the outcome lookup returns the stored
receipt, and re-running with the same operation id never applies twice.
`giggles-server` does not yet expose `once` to network clients.

## 5. Replacing a lost machine

A permanently lost voter is replaced by a new machine with a new node id and
certificate, one voter at a time, without stopping the database:

```sh
giggles-server replica status  <config.json>
giggles-server replica replace <config.json> --lost <id> --new-id <id> \
    --new-address <host:port> --new-fingerprint <64 hex> \
    --identity <operator-cert.pem> <operator-key.pem>
```

Replica admin accepts the node's own certificate or an operator certificate
listed in `replication.operators`. A peer node's certificate is refused.
Both `replace` and `status` on a follower redirect to the leader, so they need
`--identity <cert> <key>` with a listed operator certificate, or must be run on
the leader. `--identity` changes only the client certificate: the CLI still reads
the node's configuration file and private key, so it runs on a node host.

The new node starts with `"join": true` and the two surviving voters as
peers. The replacement runs six persisted steps:
1. enrol;
2. learner;
3. caught up;
4. joint configuration;
5. leave;
6. retire.

Re-running the same command after a crash or leader change resumes it. A
replacement that would leave fewer than two reachable voters is refused, and
a retired id can never rejoin.

Full procedure: the GD-0074 runbook "Replace a permanently lost voter".

## 6. Known limitations and differences

- **Isolation.** SQL transactions on the v2 engine run at read committed with
  write-write conflict detection, although sessions report `SERIALIZABLE`.
  This predates replication and applies to single-node v2 databases as well:
  write skew between two transactions is possible. It is recorded for a
  decision in GD-0074.
- **Followers serve no reads** and do not forward statements.
- **Single group.** There is one replication group per database, three voters,
  and machines in one network.
- **Transactions are bounded.** The largest transaction is 32 MiB of writes (a
  single log entry), and over-size transactions fail before any proposal.
- **Failover reopens the engine.** A new leader opens the SQL engine before
  serving, and in-flight transactions on the old leader are lost (like a
  PostgreSQL restart). In-process measurement put failover at about 0.4 s,
  most of it election (section 7).
- **Rolling upgrades.** All voters must run the same build. A build from before
  `49823f63` refuses to open a replicated store that holds `once` receipts.
- **Shutdown.** A replicated node waits for stdin to close after a `shutdown`
  line on stdin; single-node `--dev` exits on the line alone.
- **Rejoin with a wiped disk.** A voter rejoining with a wiped disk under its
  old identity is supported only mechanically. Use the replacement procedure
  with a new id instead.

## 8. The replication prototype is retired

The earlier prototype, the `giggles-node` binary in `crates/giggles-consensus`,
replicated a whole-database image and served the legacy task listeners. It was
removed after the evidence above passed (GD-0074 Q6, plan items R4-47 and
R4-48), together with the code that only existed to drive it:

- `crates/giggles-consensus`, `crates/giggles-client` (its task SDK) and
  `crates/giggles-client-conformance`;
- in `crates/giggles-faultlab`, the three-process rehearsal, its report checker
  and CLI. The TCP fault proxy (`proxy.rs`) stays;
- the `giggles-history-runtime` process test, which built `giggles-node`. The
  library stays;
- the `faultlab` task of `scripts/dev.sh` and `dev.ps1`. The `failover` task
  now runs `replication_process::three_process_failover`.

The core's legacy GD-0052 application reducer (`storage/replica/application`,
`projected_admission`, `operation_adapter`) was removed later (GD-0074 E142).
A database whose legacy format family is "application" (feature bit 3, record
namespace 9) is refused at open with an error that names the retired ledger;
GigglesDB builds at or before commit 429cbd2c can still open it. Nothing is
migrated. No server path ever wrote this ledger; only the retired prototype did.

The other 107 tests were not ported: 42 test the task protocol (authority,
approvals, disclosure budgets, task pgwire and the native task socket), which
the replicated SQL server does not offer; 2 test the whole-database image
format; and 63 test mechanisms that existed only for the prototype (the
simulated store, the faultlab child-process driver, report validator and CLI,
and the history-runtime CLI).

Properties the prototype tested more strongly than R4 does today:

- **Cancel, disconnect or deadline just before and just after a commit reaches
  the log**, in replicated mode.
- **Filling the peer port's connection limit and stalling a peer handshake.**
- **Certificate expiry** on new and established peer connections (R4 tests
  fingerprint pinning, not expiry).
- Process exit in the middle of applying an entry, and snapshot catch-up between
  real processes, are tested in-process only.

Cutting a live leader off between real processes, which only the prototype
tested, is now covered (R4-30):
`crates/giggles-server/tests/replication_partition_process.rs` puts the kept
`giggles-faultlab` proxy on each directed peer link between three server
processes and cuts a running leader off fully, one way in each direction, and
from one follower only (section 7).
