# GigglesDB R1 release notes

## 1. What R1 is

R1 is a single-node PostgreSQL 18-compatible database, available as an
embedded Rust database and as `giggles-server` for PostgreSQL clients.
Compatibility is bounded by the tested SQL and client cases below; it is
not a claim that every PostgreSQL feature or application works unchanged.

These notes cover the v2 default and the changes through `b0e62f54`.
Distributed runtime components remain separate from the single-node server.
Starting several single-node servers does not create a replicated SQL service.

For application behavior, consult the [SQL reference](../../crates/giggles-core/SQL.md).
For connection setup, consult the [server guide](../../crates/giggles-server/README.md).

## 2. Storage engine v2 is the default for new databases

The default build enables the RocksDB-backed v2 engine.
Both `giggles create` and `giggles-server --dev` now create v2 databases.
Choose the legacy engine explicitly when creating a database:

```sh
giggles create --engine legacy PATH
giggles-server --dev --engine legacy --data DIR --port 5432
```

`--engine` controls creation. Existing databases keep their engine when opened;
opening a legacy database never silently upgrades it.
The embedded `Admin::create` API retains its legacy default; embedders can
choose an engine explicitly with `Admin::create_engine`.

Builds with `--no-default-features` are legacy-only. Their creation default
is legacy, and requesting v2 returns an unsupported-engine error.

The default RocksDB build needs Rust/Cargo and libclang/LLVM:

- Windows: set `LIBCLANG_PATH` to the directory containing `libclang.dll`.
- macOS: install Xcode Command Line Tools or `brew install llvm`; set
  `LIBCLANG_PATH` to LLVM's `lib` directory if needed.

The development scripts inherit `LIBCLANG_PATH` from the environment.
See [build prerequisites](../../README.md#build-prerequisites-and-engines).
The engine default landed in commit `dd5d3b6d`.

## 3. Upgrading legacy databases

Upgrade is an explicit offline operation. Stop the server and every other
process using the database before running it:

```sh
giggles upgrade PATH
```

The upgrader never writes the v1 database files. It retains the original as
`<path>.v1-pre-upgrade-<ns>` and keeps a logical backup named
`<path>.pre-v2-<ns>.gdexp`.
Retain both alongside your independent backups while validating the upgrade.

If an upgrade is interrupted, use the recovery command for the same path:

```sh
giggles upgrade --recover PATH
```

Upgrade refuses task, receipt and other kernel records until a later release.
Check that an application's stored records fit the supported upgrade scope
before scheduling the change; keep unsupported databases on legacy.

Restored databases are upgradable. Restore-origin metadata is carried into v2,
as recorded in commit `34c70f86`. V2 restores also record the immediate source
as their origin (`d567d41a`).

The retained v1 copy is a pre-upgrade copy, not a way to downgrade subsequent
v2 writes. There is no supported downgrade of a database written by a newer
binary or engine format.

## 4. Compatibility status

The R0 harness passes **153/153 client checks**. The current recorded corpus
result is **134 compatible cases plus 3 intentional differences**.
Commit `18cf039b` records these totals; `a7c8b303` also records 153/153 clients.
The oracle is PostgreSQL 18.6.

The three intentional differences are:

- Composite-typed columns are unsupported.
- Multi-dimensional arrays are unsupported.
- Type names must be unique across schemas.

These boundaries are planned for a later type-breadth release.
Use ordinary scalar columns, one-dimensional arrays, and globally distinct
type names in the meantime.

Casts to domain types and `DROP TYPE ... CASCADE` landed in `18cf039b`.
They are no longer among these intentional differences.
Nested domains and user-typed composite attributes remain unsupported.

The [pinned matrix](../../compat/MATRIX.md) records the run at `b0e62f54`:
153/153 client checks, the per-area corpus results and the three intentional
differences, plus the ORM and GUI harness results below.

ORM migrations and model tests (`compat/orm/run.py`): Django, SQLAlchemy/Alembic,
Rails and Prisma each pass 10/10, the same as PostgreSQL 18.6. The migrations
run unchanged, including Rails' and Prisma's `timestamp(6)` columns.

GUI catalog browsing (`compat/gui/run.py`, pgAdmin 4 and DBeaver catalog
queries): 114 of 114 checks pass (PostgreSQL 114/114), including table
properties, constraints, indexes, comments and views.

### SQL added for R1 clients

- `timestamp`, `timestamptz`, `time` and `timetz` accept a precision of 0 to 6
  in `CREATE TABLE` and `ALTER TABLE ADD COLUMN`; values are rounded on write,
  and a precision above 6 is reduced to 6 with a warning.
- `UNIQUE` constraints keep their identity: they appear in `pg_constraint`
  (contype `u`) and `information_schema`, `DROP CONSTRAINT` removes their index,
  and dropping that index directly returns 2BP01.
- `COMMENT ON TABLE`, `COMMENT ON COLUMN` and `COMMENT ON VIEW`, visible through
  `pg_description`, `obj_description` and `col_description`.
- Views: `CREATE [OR REPLACE] VIEW` and `DROP VIEW [IF EXISTS] ... [CASCADE |
  RESTRICT]` for views that select columns (with aliases or `*`) from one table
  or view, `SELECT` from views (with outer filters, joins and aggregates),
  and views in `pg_class`, `pg_views`, `pg_get_viewdef` and
  `information_schema`.
- Subqueries in `FROM` over a single table with `WHERE`, `ORDER BY`, `LIMIT`
  and `OFFSET`; PostgreSQL advisory locks; `pg_tables`.

See the [harness guide](../../compat/README.md) for comparison rules,
client versions, retained reports and instructions for qualifying your SQL.
A passing case establishes the behavior exercised by that case only.

## 5. Known limitations and workarounds

- An R1-era binary cannot open databases written by newer binaries; there is no downgrade. Workaround: retain the matching binary and a pre-upgrade backup.
- GDEXP001 exports do not carry roles, owners or grants. Workaround: record and reapply security configuration separately after restore.
- V2 SQL runs at READ COMMITTED only. Workaround: use READ COMMITTED and review applications that depend on stronger isolation.
- The `giggles-export` archive refuses uuid, jsonb and array columns. Workaround: keep those schemas out of that archive workflow and validate an alternative backup path.
- On v2, single statements beyond 1,024 rows work for INSERT (VALUES, INSERT ... SELECT, ON CONFLICT), COPY FROM (text and CSV), UPDATE and DELETE. That includes tables with secondary indexes, FK checks and referential actions (RESTRICT, NO ACTION, CASCADE, SET NULL, SET DEFAULT, ON UPDATE CASCADE), primary-key changes and IN / EXISTS subqueries. Remaining limits: UNIQUE checks keep a bounded per-page witness; changed self-references, NO ACTION-only action graphs and expected-version paths keep a whole-table fallback that is limited to 1,024 indexed rows; PK-changing updates whose WHERE is served only by a secondary index scan the table in pages. The legacy engine keeps its 1,024-row statement limit. Workaround: batch operations that hit these shapes, or use v2.
- Large UPDATE performance remains behind PostgreSQL: 1M rows takes about 69 s versus about 4 s in PG. Workaround: budget maintenance time and measure representative workloads.
- RETURNING is buffered with a 1 MiB retained-output budget. Workaround: return fewer columns or process smaller batches.
- On v2, space from dropped tables and indexes, and from interrupted index builds, is reclaimed once no active snapshot can still see it: at open, after a commit that dropped a table or index, and on demand through `Admin::reclaim_storage()` (`2615cbdb`). Plain DML never triggers reclamation, and RocksDB compaction decides when files actually shrink. Legacy does not reclaim. Workaround: expect disk usage to fall some time after a DROP, not immediately.
- SUM and AVG over integer, bigint and numeric inputs share a statement-wide work budget, so on large inputs (roughly 100k or more non-null rows) they fail with 54000. COUNT, MIN and MAX stream on v2 and are not affected. Workaround: aggregate in smaller ranges, or pre-aggregate.
- Secondary indexes on numeric and timestamptz columns are not yet supported (0A000). Workaround: index an integer or text surrogate column.
- Correlated scalar subqueries (a subquery used as a value) are not yet supported (0A000). Correlated EXISTS / NOT EXISTS and IN are supported. Workaround: rewrite as a join or EXISTS.
- VACUUM and ANALYZE are not supported (0A000); v2 maintains storage without them.
- Nested domains and user-typed composite attributes are unsupported. Workaround: use domains over built-in scalars and built-in composite attribute types.
- Views may only select columns from a single table or view; other definitions (WHERE, joins, aggregates, expressions, DISTINCT, LIMIT) return 0A000. Workaround: put that logic in the querying statement, or use a table.
- Reading a view requires SELECT on the view and on every table and view beneath it; PostgreSQL checks the underlying tables with the view owner's rights instead. Workaround: grant SELECT on the underlying tables to roles that read the view.
- INSERT, UPDATE and DELETE on a view return 0A000 (PostgreSQL updates simple views automatically), and views report is_updatable NO. Workaround: write to the underlying table.
- `pg_get_viewdef` returns an equivalent single-line definition with quoted names and explicit aliases, not PostgreSQL's formatted text; the pretty and wrap arguments are ignored.
- CREATE VIEW requires SELECT on the source when the view is created (PostgreSQL checks it when the view is read).
- Comments are limited to 65,536 bytes (54000 beyond that).
- A non-superuser running `DROP TABLE IF EXISTS` or `DROP VIEW IF EXISTS` on an object that does not exist gets 42501 rather than a notice. Workaround: run such drops as the owner role or a superuser.
- Databases that use a UNIQUE constraint, COMMENT ON or a view cannot be opened by binaries built before those features (they refuse at startup with an unsupported-format error). UNIQUE indexes created before `4235d3ff` stay plain unique indexes; recreate the constraint to get `pg_constraint` rows.

The large-DML scope, RETURNING budget and 1M-row timing are recorded in
`a7c8b303` (68.9 s versus PostgreSQL 18.6's 4.3 s in that measurement).
This is a recorded workload result, not a throughput guarantee.
The archive refusal is recorded in `22898efc`.

Large-table index builds and DDL no longer inherit the legacy 1,024-row cap
on v2 (`2065ab2f`). DROP TABLE and DROP INDEX unpublish objects atomically;
physical cleanup is deferred. Plan capacity with that distinction in mind.

## 6. Operator notes

### Durability and crash qualification

`compat/v2_qualification.py` drives a real `giggles-server` process on v2 and
checks it from an independent PostgreSQL 18.6 `psql`. The R1 run (commit
`d5e54425`, seed 7731, debug build, one shared Windows machine) passed every
cell:

| Cell | Result |
|---|---|
| Kill under load | 3/3 forced process-tree kills (`taskkill /T /F`) during a concurrent transfer and insert/update/delete workload. After each restart: no acknowledged commit was lost (27 of 27 in the last iteration); every surviving transaction matched one the client issued; no transfer was partly applied; the balance total was unchanged; the unique index had no duplicates |
| Kill during DDL | `CREATE INDEX` and `ALTER TABLE` killed mid-flight were absent after restart; an acknowledged `DROP TABLE` stayed dropped |
| Large load | 5,000,000 rows with two secondary indexes, about 2,400 rows/s, 1.23 GB on disk; restart in 16 s; `count`/`min`/`max`, indexed point lookups and an indexed `ORDER BY` range correct after restart |
| Large SUM | Known limit: `sum()` over 5,000,000 rows fails 54000 (see section 5) |
| Backup and restore | `giggles export` then `giggles restore` of the 5,000,000-row database; the restored v2 database passed the same checks |

Restoring 5,000,000 rows took about 31 minutes in that debug build.

A second run at tens of gigabytes (commit `579b5178`, seed 7731, release
build, same machine) also passed every cell except the known SUM limit:

| Cell | Result |
|---|---|
| Kill under load | 3/3 forced kills; no acknowledged commit lost (87 of 87 in the last iteration) |
| Kill during DDL | A `CREATE INDEX` killed mid-flight was absent after restart; acknowledged `ALTER TABLE` and `DROP TABLE` were durable |
| Large load | 32,600,000 rows with a 512-byte payload each, loaded with `COPY` at about 11,500 rows/s (8.8 MB/s): 25.0 GB on disk. Restart in 7.4 s; counts, `min`/`max`, indexed lookups, an indexed range and sampled payloads correct after restart |
| Large SUM | Known limit: `sum()` fails 54000 (section 5) |
| Backup and restore | The export was 22.9 GB and took about 80 minutes; restore took about 84 minutes. The restored database passed the count, index and sampled-payload checks |

Measure your own export and restore times before relying on them for
recovery planning.

This is evidence from one machine and workload, not a production guarantee.
Validate backup and recovery with your own data before deployment.

The core `giggles` CLI provides these export, verification and restore commands:

```sh
giggles export PATH BACKUP.gdexp
giggles verify BACKUP.gdexp
giggles restore BACKUP.gdexp RESTORED_PATH
```

These are the command forms accepted by
[`giggles.rs`](../../crates/giggles-core/src/bin/giggles.rs).
Use a separate restore destination and verify the resulting database before
switching an application to it. Do not confuse these core commands with the
separate `giggles-export` archive tool and its type restrictions.

The IDE also includes **Backup verify and restore** and **Export verify and
import** configurations. Their task workflows are distinct; consult the
[development guide](../../scripts/README.md) before choosing one.

Development mode binds to loopback, disables TLS and defaults to SCRAM-SHA-256
password authentication. On first start it prints a generated owner password
once; save it, or set a nonempty `GIGGLES_OWNER_PASSWORD` before first creation.
Restarting the same data directory retains the password without printing it.
The `CONFIG.json` server workflow provides the separate mTLS configuration.
See the [server guide](../../crates/giggles-server/README.md) for credential
setup and offline owner-password reset.

## 7. Building and running

From the repository root, build the core administrative CLI and server:

```sh
cargo build --locked --manifest-path crates/giggles-core/Cargo.toml --bin giggles
cargo build --locked --manifest-path crates/giggles-server/Cargo.toml --bin giggles-server
```

For a legacy-only build, append `--no-default-features` to either command.
Use the libclang/LLVM setup in section 2 for default builds.

For a local PostgreSQL development server, the scripts manage build outputs
and data outside the checkout:

```powershell
./scripts/dev.ps1 -Task dev-server -Port 5432
```

The Windows script defaults to `J:/gigglesdb-work/ide`; use
`-Work J:/gigglesdb-work/MY-SESSION` to isolate another instance.
The macOS equivalent is:

```sh
./scripts/dev.sh --task dev-server
```

With the built binary on PATH, an explicit development invocation is:

```sh
giggles-server --dev --data DIR --port 5432
```

The database lives at `DIR/db`. Connect to `127.0.0.1:5432`, user `postgres`,
database `postgres`, with TLS disabled and the saved owner password.

Shared IntelliJ configurations live in [`.run/`](../../.run/):
**02b Dev server, password auth** runs the development server.
On macOS, **02c Dev server v2 engine, password auth (macOS)** explicitly
selects the v2 workflow and its separate data directory.
For the configured mTLS demo, run **01 Setup local demo**, **02 Server**,
then **03 Client Ping**. These are separate from the password-auth dev mode.
See the [IDE setup and run guide](../../scripts/README.md) for the full list.
