# GigglesDB R3 release notes

Design, plan and evidence: GD-0061 (AI-agent safeguards).

## Legacy task prototype retired

R3 defines tasks in SQL (`CREATE TASK`). The earlier task prototype is
retired from the default build. This section lists what changed for users.

### What is gone from default builds

The default `giggles-core` and `giggles-server` builds no longer contain:

- the task prototype API: granting, revoking and approving tasks, the
  executor, task resources, and the task subcommands of the `giggles` CLI;
- the fixed repair rows: the one-statement repair grammar
  (`UPDATE deliveries SET status = ... WHERE tenant ...`, `parse_repair`)
  that tasks ran against the fixed delivery rows;
- the `GIGGLES <JSON>` text protocol on the PostgreSQL listener;
- the legacy server requests: Preview, Execute, RepairSql and Status, over
  JSON and protobuf.

All of it remains available behind the non-default cargo feature
`legacy-task` on both crates (`giggles-server`'s feature enables
`giggles-core`'s). Building with that feature gives the previous behaviour.

### Behaviour changes in a default build

- **Task certificate bindings are rejected.** A server config that binds a
  certificate to `"role": "Task"` fails to load with: `role Task is the
  retired legacy task prototype; enable the legacy-task feature or bind the
  certificate to NoSql/Application/Database`. A certificate that should have
  no SQL authority can be bound to the new `NoSql` role, which answers Ping
  only.
- **`GIGGLES` text gets 42601.** A SQL session that sends `GIGGLES ...` now
  gets the ordinary parser's syntax error, SQLSTATE 42601 (it was 42501
  before). PostgreSQL also returns 42601 for unknown syntax.
- **Legacy API requests are refused.** The JSON request names `preview`,
  `execute`, `repairSql` and `status` return INVALID_ARGUMENT with "retired
  legacy task prototype". Protobuf `ExecuteRequest` fields 3-6 are reserved;
  a request that uses them decodes as having no request and returns
  INVALID_ARGUMENT.
- **`Role::Application` is unchanged.** Application bindings and the
  application ledger behave as before.

### Existing databases and upgrade

- No data is migrated. Task records are not converted into R3 tasks.
- A legacy database that holds task records still opens, and its SQL tables
  read as before. A default build has no API to act on the task records.
- `giggles upgrade` (upgrade to v2) refuses such a database and leaves its
  files unchanged. The message lists each kind of record found with its
  count:

  ```
  upgrade refused: this database holds records of the retired task prototype (tasks: 1). They are not migrated to v2 (GD-0061). Export the SQL tables, restore them into a new v2 database, and define tasks there with CREATE TASK.
  ```

  It replaces the earlier `upgrade cannot represent ...` message.
